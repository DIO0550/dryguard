# テスト規約

**前提**: テストの配置（`#[cfg(test)] mod tests`）・命名（`test_<対象>_<条件>_<期待結果>`）・
`assert!` の使い分けなど**言語共通の規約は d-market-rust の `testing` スキル**が持つ。
ここに書くのは、それに足す分だけ（`AGENTS.md`「規約の持ち場」）。

## 前提として守るもの（プラグイン側の再掲はしない）

- `#[cfg(test)] mod tests` によるモジュール内テスト
- テストケース名は `test_<対象>_<条件>_<期待結果>` 形式・英語
- 正常系・異常系・境界値
- `assert_eq!`（値の比較）/ `assert!(matches!(..))`（バリアントの検証）/ `assert!` + メッセージ

## テスト内の unwrap / expect

**使ってよい。** 禁止の対象は本番コードだけで、テストは失敗理由が分かるほうが優先される。

`clippy.toml` の `allow-unwrap-in-tests` / `allow-expect-in-tests` がこれを許可している。
`expect()` にはメッセージを付ける（何を前提にしていたテストが崩れたのかが出る）。

## 振る舞いをテストする

テストは**外から観測できる振る舞い**に対して書く。内部のヘルパー関数・中間データ構造・
処理順序はテストしない。

- テスト名は**仕様の文**として書く。「`rsplit_once` が呼ばれる」ではなく
  「Windows のドライブレターを区切りと取り違えない」
- 1 テスト 1 振る舞い
- **リファクタリング耐性を判断基準にする。** 振る舞いを変えずに実装を書き換えたときに
  壊れるテストは、実装詳細をテストしている

## assert は「落ちうるか」で見る

テスト名が仕様の文になっていても、assert がその仕様を捉えていないことがある。
**その assert を通すために実装をどう壊せるかを考える。** 壊し方が思いつかないなら、
そのテストは何も守っていない。

### 既定値と違う答えになる入力を選ぶ

「規則で決まる答え」と「既定値」が同じ入力を使うと、規則を丸ごと壊しても既定値のほうで通る。

```rust
// NG: --lang の既定が Auto なので、Auto を渡しても指定が効いたか分からない
let cli = parse(&["dryguard", "compare", "a.ts:10", "b.ts:20", "--lang", "auto"]);
assert_eq!(cli.options.lang, LanguageOption::Auto);

// OK: 既定と違う値を選ぶ
let cli = parse(&["dryguard", "compare", "a.ts:10", "b.ts:20", "--lang", "ts"]);
assert_eq!(cli.options.lang, LanguageOption::Ts);
```

### 「出ない」を確かめるときは、対照を 1 件置く

そもそも該当するものが入力に無い状態で「出ない」を確かめても、実装が何をしても通る。
**同じ入力の中に出る側を 1 件置き、期待値を「その 1 件だけ」にする。**

dryguard で言えば、**`DO-NOT-EXTRACT` が出ないことを確かめるテストに、そもそも
似たペアが存在しない入力を使わない。**

### 迷ったら、その 1 件だけ実装を壊して走らせる

全体のミューテーションテストは重いが、疑わしい assert 1 つのために分岐を消して
1 ファイル回すだけなら数秒で済む。**頭で判断せず確かめる。**

## モックは使わない

依存は実物を使い、相互作用（呼び出し回数・引数）ではなく**結果の状態・戻り値を検証**する。

- `stage1` / `stage3` は純粋なので**実物で検証できる**。ここでのモック・スタブは全面禁止
- 代替してよいのは**プロセス外・制御不能な境界のみ** = `lsp` が包む外部プロセス
- その場合もモックライブラリより、**テスト用の単純な実装（フェイク）**を優先する

## LSP を要するテストは、飛ばしたことが分かる形にする

サーバが入っていない環境では実行できないテストがある。**黙って通さない。**
`#[ignore]` を付けて理由を書くか、サーバの有無を見てスキップしたことを出力する。

**Why**: 通ったのか検査されなかったのかが区別できない状態は、`.claude/hooks/README.md`
「フェイルオープンかつサイレント」と同じ失敗の形。CI ではサーバを入れて実際に走らせる。

## テスト用ヘルパーの置き場所

**テストに書こうとしているヘルパーが汎用の操作なら、それは実装側に足りていない機能。**
テストモジュールにその場しのぎで書かず、実装側へ置く。

判断軸: そのヘルパーは**テストであることに依存しているか**。`assert` を含む表明はテスト固有だが、
「値を組み立てる」「別の表現へ直す」は汎用操作なので実装側に置く。

同じヘルパーを 2 つ以上のテストモジュールに書いたら、その時点で共通化する。

## ステージをまたぐテストと単体のテストを分ける

- 各ステージの振る舞いは、そのモジュール内の `mod tests` で見る
- ステージをつないだ結果は `tests/`（統合テスト）で見る
- **単体で見られるものを統合テストに寄せない。** 落ちたときに原因の範囲が広がる
