# TDD 規約

**前提**: Red-Green-Refactor のサイクル・粒度・境界値テストの扱いは **d-market-rust の `tdd`
スキル**が持つ。ここに書くのは、それに足す分だけ（`AGENTS.md`「規約の持ち場」）。

## 前提として守るもの（プラグイン側の再掲はしない）

- **Red**: 失敗するテストを書く。Rust ではコンパイルエラーも Red として扱ってよい
- **Green**: 通る最小限のコード。テストが要求しない機能を先回りで実装しない
- **Refactor**: 重複の排除・関数分割・定数化・`cargo fmt` と clippy の解消
- **1 サイクル = 1 つの振る舞い（1 テストケース）**
- 境界値・網羅テストは最後の Refactor フェーズで回帰テストとして追加する
- 既存コードへのテスト追加はサイクル外（特性テスト）

## どこに TDD が効くか

このツールは、TDD が回しやすい層と回しにくい層がはっきり分かれている。
**回しにくい層は、回せる形に切り出してから書く。**

| 層 | TDD | 理由 |
|---|---|---|
| `stage3`（分類） | **最も効く** | 純粋。シグナルの組み合わせごとに期待するラベルを先に書ける |
| `stage1`（候補抽出） | 効く | 純粋。入力のソースと期待するチャンク・類似度を先に書ける |
| `cli` | 効く | 引数の並びと期待する解釈を先に書ける |
| `lsp` | **回しにくい** | 外部プロセスが要る |

## `lsp` は「応答を受け取ってから先」を切り出す

外部プロセスとの会話そのものは TDD にできないが、**受け取った応答を
こちらの型へ直す変換は純粋関数**にできる。そこを切り出して TDD の対象にする。

この切り分けは `rules/architecture.md` の依存方向（`stage3` は `lsp` を直接触らず、
シグナルとして受け取る）と一致する。**テストのために構造を歪めているのではなく、
歪んでいない構造がテストしやすい。**

## 判定ルールを変えるときは、先にテストを足す

`stage3` の判定は**このツールの価値そのもの**。閾値や決定木を触るときは、
**変えたい振る舞いを表すテストを先に書いて Red にする**。

「実データで見たらこうなってほしかった」を、実データを見た回だけの直しで終わらせない。
そのケースをテストにしておかないと、次に閾値を触ったときに黙って戻る。

## 雛形は最初の Red の前に消す

`cargo init` が生成する `add` 関数と `it_works` テストは、最初の Red の前に削除してよい。
