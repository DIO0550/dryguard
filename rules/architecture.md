# アーキテクチャ規約

**このファイルは dryguard 固有の構造規約。** 言語共通の Rust 規約は d-market-rust の
`rust-rules-plugin` が持つ（`AGENTS.md`「規約の持ち場」）。

## 3 ステージのパイプライン

```
config(設定の読み取り)
  ↓
cli → pipeline → classification(分類) → semantics(意味情報収集) → syntax(候補抽出)
        ↓  ↓                                    ↓
        │ codebase(走査対象の収集)              lsp(外部プロセスとの境界)
       report(text / JSON 化)
```

| モジュール | 責務 | 持たないもの | 計画での呼び名 |
|---|---|---|---|
| `cli` | 引数の受け口と値の解釈 | 判定・I/O の手順 | — |
| `config` | `dryguard.toml` を読んで、外から動かせる閾値とドメインの宣言にする | 判定・**既定値**・宣言の照合 | — |
| `pipeline` | ステージを呼ぶ順序 | 判定・チャンク化 | — |
| `codebase` | 走査対象のファイルを集めて読む | 判定・チャンク化・順序 | — |
| `syntax` | チャンク化・AST 正規化・類似度・import 収集 | 判定 | Stage 1 |
| `semantics` | LSP への問い合わせと応答の正規化 | 判定 | Stage 2 |
| `classification` | シグナルの統合と判定・理由の組み立て | I/O・LSP の呼び出し | Stage 3 |
| `report` | 判定と根拠を、人が読む text とエージェントが読む JSON にする | 判定・シグナルの再計算 | — |
| `lsp` | 子プロセスの起動と JSON-RPC | 複数ステージにまたがる手順 | — |

**モジュールは段の番号ではなく責務で呼ぶ。** `stage1` は「パイプラインのどこにいるか」しか
言っておらず、何をするモジュールなのかを伝えない（`rules/naming.md`「内容を表さない
汎用語を使わない」と同じ形）。`syntax` と `semantics` を分けた名前にしておくと、
**このツールの主張（構文が似ていることと意味が同じことは別物）がモジュールの分かれ目に出る。**

**Why not（`structure` / `candidates`）**: 「構造類似度」というシグナル名、
「候補ペア」という値と、それぞれモジュール名が競合する。

計画（`docs/dryguard-plan.md`）と Issue が使う「Stage 1 / 2 / 3」は**段を指す呼び名として残す**。
どちらから来た読者も辿れるよう、対応は上の表で引く。

## 依存方向のルール（必須要件）

- **`syntax` は `semantics` / `classification` を知らない。** 知った時点で
  「LSP 無しでも動く」が壊れる。Phase 0 が LSP を飛ばして成立しているのはこの分離があるため
- **`classification` は `lsp` を直接触らない。** 意味情報は**シグナルとして受け取る**。
  LSP が使えない環境でも判定できる形を保つ
- **`lsp` はオーケストレーションを持たない。** 外部プロセスとの会話と、応答を
  こちらの型へ直す変換に閉じる。複数ステージを組み合わせる手順は `pipeline` の責務
- **`config` は既定値を持たない。** 持つのは**書かれていたかどうか**と、書かれていた値だけ。
  書かれていないキーに何を当てるかは `classification` が決める（下の「判定は 1 箇所にだけ
  置く」）。両方が既定値を持つと、片方だけ直したときに**`--explain` が出す閾値と、
  判定が当てた閾値が食い違う**
- **`classification` は `config` を知らない。** 外から動かせる閾値は
  `ConfiguredThresholds` として**受け取る**。設定ファイルが無くても・読めなくても
  判定そのものは同じ形で動く（`lsp` を直接触らないのと同じ形）
- **ドメインの宣言の型と照合は `domain_declaration` に置き、`config` に置かない。**
  宣言を持つのは `semantics`（呼び出し元・呼び出し先の数え方）と `classification::signal`
  （モジュール距離）で、`config` に置くと `classification` が `config` を知ることになる。
  `domain_declaration` は `threshold` と同じく**どこからも使う値の型**で、I/O を持たない。
  **`syntax` は宣言を知らない** — 段数は宣言に関わらず測り、宣言で重ねるのは `pipeline`
- 循環依存は全面禁止

## 判定は 1 箇所にだけ置く

**シグナル → ラベルの決定木は 1 箇所にだけ書く。** `syntax` や出力側に判定が漏れると、
`--explain` が出す根拠と実際の判定が食い違い、**このツールの価値（説明可能性）が壊れる**。

「ここで先に弾いておけば速い」は判定の漏れ出しなので、やらない。速度は `syntax` の
候補列挙で解決する。

**閾値の既定値も同じ 1 箇所が持つ。** 外から動かせる閾値は `ConfiguredThresholds` に
束ねてあり、**指定が無かったキーに何を当てるかを決めているのはそこだけ**。設定を読む側
（`config`）にも既定値を置くと、片方だけ直したときに**設定を書いた人と書かなかった人とで
違う決定木が走る**。

**外から動かせるものと動かせないものを、型で分ける。** `ConfiguredThresholds` は
`--threshold` / `dryguard.toml` が動かす 3 つだけを持ち、`SEPARATE_DIRECTORY_STEPS`
（ディレクトリの段数）と `SHARED_CALLEE_DOMAINS_THRESHOLD`（呼び出し先ドメインの重なり）は
持たない。**どのシグナルに何を当てるかを組むのは
`AppliedThresholds::of` の 1 箇所**で、そこだけが両者を合わせる。

**同じ 1 箇所が「取れなかったシグナルの扱い」も持つ。** シグナルから傾き
（`classification::reason::Lean`）を出すところと決定木は同じモジュールにあり、
**取れなかったシグナルはどちらへも傾けない**（表と方針は `classification` の module doc）。
欠けた数を数えて判定を弱める規則を別に足すと、**`--explain` が出す根拠を全部足しても
判定を再現できなくなる**ので、足さない。断定に要る根拠が揃わなければ `REVIEW` へ寄るのは、
弱めた結果ではなく証拠が揃わない結果。

**これは下の「既定値で埋めない」とは別の話。** 埋めないのは**シグナルの値**
（取れなかった理由を持ったまま運ぶ）で、傾きは**その値から出す答え**。取れなかった
シグナルから傾きが出ないのは、既定値で埋めたのではなく**材料が無い**から。

## 取れなかったシグナルを既定値で埋めない

LSP が起動しない・`callHierarchy` が使えない・チャンクが切り出せないは、**すべて
「取れなかった」として構造に出す**。0.0 や「中立」で埋めると、実際にその値だったのか
取れなかったのかを後段も読者も区別できない。

これは `rules/coding.md`「不正な状態を型で表現できなくする」の適用でもある
（`f64` ではなく「取れた / 取れなかった」を持つ型で受ける）。

| NG | OK |
|---|---|
| `similarity: f64` に取れなかったとき 0.0 を入れる | `Option<Similarity>` で不在を表し、`--explain` に理由を出す |

### どこまでを「取れなかった」に数えるか

**そのシグナルの答えに効く材料が欠けたときだけ「取れなかった」にする。**
効かない材料が欠けたのは、取れたのと同じ扱いでよい。

材料が 1 つ欠けるたびに「測れない」を増やすと、**判定に効かない欠けまで測れないになる**。
逆に欠けを黙って落とすと、**確かめられなかったことを確かめた答えとして出す**。
線引きが言葉になっていないと、どちらに倒すかが巡ごとに変わる。

型シグネチャがこの適用。**比較に残る綴りを、指す先まで辿れたか**で決める
（型名なら宣言まで、型名でなければ尋ねる位置を作れるか）。

| 比較に残る綴り | 判定 | なぜ |
|---|---|---|
| 辿って開けた | 落とす（差し込んだ綴りで比べる） | 答えが出ている |
| 辿ったが開けなかった | 「測れない」（理由まで出す） | 開けていれば重なったかもしれない。綴りのまま比べた結果は答えにならない |
| **そもそも尋ねていない** | **「測れない」** | **確かめていない**。綴りが一致しただけのものを「重なる」と答えることになる |
| **そもそも型名でない** | **「測れない」** | **尋ねる位置を作れない**。指す先が書かれた場所で決まるので、綴りが一致しただけのものを「重なる」と答えることになる |

比較に残らない綴りの型名は、どれであっても落とす。差し込みで消えた・正規化で落ちた名前は、
**辿れても辿れなくても同じ答えになる**。

**「尋ねていない」の中身は 3 通りあり、言い切れることが違う**
（`semantics::type_signature` の `UntracedReason`）。

| 中身 | 言い切れること | 出し方 |
|---|---|---|
| そのチャンクが**注釈を省ける位置**の注釈を省いた | **注釈が無いことを構文木から確かめてある** | 直す先を出す（注釈を書く） |
| 比較に残る綴りの型名に、辿った記録が無い | **書かれていないのか、集め損ねたのかを区別できない** | 直す先を言い切らない |
| **ソースの引数の数と綴りの引数の数が揃わない** | **どの引数が注釈を省いたのかを言えない** | 直す先を言い切らない |

値の型の注釈を省いた関数と、**既定値を書いて引数の注釈を省いた**関数では、hover の綴りの
その位置に推論された型名が現れるが、構文木のどこにもその名前が無いので `typeDefinition` を
向ける位置を作れない（`syntax::type_reference`）。これが 1 行目。

**ただし引数でこれを出すのは、辿った記録がある綴りに限る。** 引数の型は**チャンクの外に
書かれた注釈**から来ることがある（名前付き関数式が代入先の注釈から引数の型を受け取る形）ので、
引数リストに注釈が無いことは**ソースのどこにも書かれていないことを意味しない**。
記録が 1 つも無いときは 2 行目を先に出す（`semantics::type_signature` の `single_outcome_of`）。
**値の型にこの抜け道は無い** — 外側の注釈が綴り全体を決める形は `syntax::chunk` の
`AnnotatedPositions::AllWritten` が先に畳む。

**Rust の引数のないエイリアスの右辺の型名は、宣言側ソースの位置から解決する。**
`syntax::rust_callable::RustAliasSource` が declaration site の位置と一致する宣言を読み、
右辺の型名・プリミティブ表記の問い合わせ位置を返す。`semantics::resolved_type` が
そのファイルを開かせ、hover と definition でエイリアスの連鎖も辿る。
使用側の同名の宣言記録や型変数は流用しない。直接書かれた型もエイリアスの右辺も、
具体的な型はファイルと UTF-16 の宣言位置から作る `declared type identity` で比較する。
局所名・再輸出名・パスの綴りに依存せず、型引数は正規化して保持する。
導入した綴りは使用側で再解釈せず、型変数に捕捉させない。

**プリミティブ表記も使用側・宣言側の両方で確認する。** hover が単独のプリミティブを
返せばその型を保持し、別の型を指すならその位置の definition を辿る。
ソースを読めない・問い合わせ未提供・読めない応答は既存の理由を保持する。
`typeDefinition` の空の応答だけでは、別のプリミティブへのエイリアスを除外できない。
循環は declaration site の組で検出して `CyclicAlias`、エイリアスの展開が 32 段を
超える、または展開した右辺が 64 KiB を超えると `AliasExpansionLimit` を返す。
ソースと再帰しない終端だけをキャッシュし、
展開済みの連鎖や深さに依存する失敗はキャッシュしない。

**通常の型エイリアスのジェネリック宣言の右辺・既定値は、プリミティブと束縛された型パラメータに閉じるものに限る。**
型引数は使用側で正規化してから当てはめ、入れ子と既定値（先行する型パラメータ参照を含む）を
展開する。導入した引数は再置換せず、展開後に型変数を初出順で番号付けし直す。
宣言の型パラメータと同名のプリミティブ表記は束縛された変数として扱う。
通常の型エイリアスの境界は当てはめ時の制約に加えない。
ライフタイム・const 引数付きの宣言、別の型名や定数名を含むジェネリックの右辺・既定値、
引数の個数・種類の不一致は `UnopenableAlias`。展開候補の右辺・既定値は宣言側ソースの
プリミティブ表記への hover で確認し、shadow されていたら開かない。
型引数を取らない宣言の配列長は、下の評価経路で値を確定する。未知の型構文・関連型の選択は開かない。
差し込みは `syntax::rust_callable` が型名のノードで行い、束縛された型変数には行わない。

**Rust の直接の配列長と、型引数を取らないエイリアス RHS の配列長は、宣言側で値を評価する。**
`syntax::rust_callable::RustArrayLengths` が式・置換範囲・元の UTF-16 位置を持ち、
`semantics::resolved_type::array_length` が整数と自由な usize 定数を評価する。
定数は出現位置への hover が安定してから一意な definition で辿り、宣言側の
`usize` 表記もプリミティブへの hover で確認する。使用側の同名定数は流用しない。
対応は10/16/8/2進の整数（区切りと usize suffix）、`+ - * / %`、括弧、単一式のブロック。
関数本体の式は含めない。const generics の当てはめ・関連定数・ジェネリックエイリアスの
自由定数は対応しない。演算は checked で行い、中間値も最小の usize 幅に収まる
65535 以下に限る。宣言連鎖は32段、式は32段・128ノード、評価全体は1024ステップまで。
ソースだけをキャッシュし、評価済み連鎖と深さに依存する失敗はキャッシュしない。
循環は declaration site で検出して `CyclicArrayLength`、値・式・連鎖・作業量の上限は
`ArrayLengthEvaluationLimit`、未対応構文・無効な演算・一意に選べない定数は
`UnevaluableArrayLength` として測定不能にする。LSP とソース読み込みの失敗理由は保持する。

**関数 hover の `{const}` は、型構造の対応を確認してからソースの値へ置換する。**
両側の配列長を出現番号へ置換して `RustCallable` で正規化し、全体が一致するときだけ
同じ位置の値を差し込む。個数だけの一致では引数と戻り値を取り違える。
hover に具体的な整数が残る場合は評価値との一致も確認し、未知の式は印として扱わない。
対応できなければ `UnmatchedArrayLength`、未評価の式は綴りで比較しない。

**Self を含む関連型は、直接囲む trait impl の定義か、型変数の付け替えだけで一致する impl の
定義に限って展開する。**
`syntax::rust_callable::RustProjectionSource` が投影の末尾の位置と直接の impl から
一意な関連型定義を読み、`semantics::resolved_type` が definition の返した trait メンバーの
所有 trait と impl の実装 trait の宣言位置を照合する。完全修飾形は対象が Self 自体で、
trait と型引数が同じソースの束縛環境で一致するものに限る。
RHS の名前は定義側の位置から辿り、impl 型変数と GAT の型引数はそれぞれの束縛元を保って
正規化した後に代入する。**RHS の単独の Self は使用側の impl の対象型を代入する**
（`RustTypeResolution::Associated` の `substitutes_self`）。RHS を書いた impl の対象型は、
直接囲む impl ならそれ自身、選んだ impl なら束縛と宣言元の照合で使用側の対象型と
一致を確かめてあるので、候補側の構文から綴り直さない。そのため使用側のソースも、
Self を含む投影を歩くときに対象型の型名を尋ねる位置として集める。
条件付き・複数の定義、入れ子の投影・RHS の中の投影（`type Item = Self::Other`。Issue #327）は
`UnresolvedAssociatedType`、未対応の RHS・ライフタイム GAT・型引数の不一致は
`UnopenableAssociatedType`。具体的な型は関連型の名前や宣言元ではなく、展開した RHS で比べる。

**直接囲む impl が別 trait の impl・inherent impl なら、完全修飾形の trait の impl を選ぶ。**
`syntax::rust_callable::RustQualifiedProjection` が使用側の trait 引数と対象型を、
`RustImplCandidate` が `implementation` の返した impl を読み、`binding_with` が
**候補の型変数を使用側の impl の型変数へ付け替えるだけで構文が揃うか**を確かめて、
同じ位置の型名の組を返す。組は `semantics::resolved_type` が両側のソースの位置から辿り、
具体的な宣言元か確かめたプリミティブ・開いた右辺が等しいときだけ一致にする（綴りでは比べない）。
一致する候補がちょうど 1 つのときだけ、その RHS を候補側のソースで解決して展開する。

- **選んでよい根拠は coherence。** 付け替えで一致し境界を持たない impl があれば、他の impl は
  重ならない。だから blanket impl を含む残りの候補を数えず、読めない候補も飛ばしてよい
- **選ばないもの**（偽陰性側）: 型変数が具体的な型に当たる候補・境界や where 句・const 引数を
  持つ候補・blanket impl（Issue #318）、属性（`cfg` など）付きの候補と `default impl`、
  使用側の where 句に**左辺が型変数そのものでない述語**がある形（Self や対象型を別の綴りで
  書いた param-env の候補でありうる。rustc も param-env を優先して正規化しない）、
  短縮形・入れ子の投影（Issue #327）
- **理由**: implementation を提供しない・空は `ImplementationNotProvided` /
  `NoImplementationSite`。一致が 2 つ以上なら `UnresolvedAssociatedType`。0 件なら、照合まで
  進めたが辿れなかった候補の理由 → 候補のファイルを読めない（`UnreadableDeclaringDocument`）→
  URI を読めない（`UnreadableImplementation`）→ `UnresolvedAssociatedType` の順
  （`semantics::resolved_type` の `UnselectedImpls`）
- **`const trait` は読めない。** tree-sitter-rust が `pub const trait` を構文エラーにするので、
  std の多くの trait（`Iterator` / `Deref` など）は所有 trait を照合できず
  `UnresolvedAssociatedType` に倒れる

**書かれた型名がここに来ることはある。** `syntax` が集めた型名は必ず尋ねる（TypeScript は
`pipeline`、Rust は hover の後に `semantics::type_signature` が尋ねる）が、
**集める場所の一覧に漏れがあれば、書かれた型名が集まらない**（名前付き関数式が代入先の
注釈から引数の型を受け取る形。Issue #188）。一覧は TypeScript の文法が持つ形の数だけ
増え続けるので、**漏れは前提として設計する**（`rules/coding.md`「列挙で判定を組むときは、
漏れの倒れる向きを選ぶ」）。**倒れる向きは偽陰性のまま**で、漏れても綴りのまま比べには
行かない。変わるのは出方だけなので、そこを 2 行目として分けてある。

**Why not（1 語のままにする）**: 漏れたときに `--explain` が「型注釈を書くと辿れる」と出すと、
**注釈はもう書かれている**利用者に嘘の案内を出すことになる。`unopened` を理由ごとに分けて
いるのと同じ形（`rules/coding.md`「エラー型は原因ごとにバリアントを分ける」）。

**数える単位は型名 1 つではなく、綴りの中の出現 1 つ。** 1 つのシグネチャに同じ綴りが
2 回現れ、片方だけがソースに書かれていることがある（`function build(a: Amount): Amount` の
戻り値の注釈を省いた形）。辿った記録を**綴りで引く**と、書かれていないほうが書かれたほうの
記録に乗り、**別々のモジュールの `Amount` が単一化可能に出る**（偽陽性）。

**出どころを出現ごとに持てるのは、注釈を省ける位置だけ。** hover の綴りとソースの綴りは
別物なので、出現の位置どうしを突き合わせる鍵が無い。代わりに `syntax` が
**そのチャンクの宣言が、注釈を省ける位置それぞれに注釈を書いたか**を運び（`syntax::chunk` の
`AnnotatedPositions`。`rules/naming.md` の `annotatable position`）、省かれていれば
**その位置に出た型名は綴りで引かずに「尋ねていない」へ倒す**
（`semantics::type_signature` の `NormalizedSignature::spelled_positions`）。

| 注釈を省ける位置 | 綴りに残る型名 | 判定 |
|---|---|---|
| 注釈が書かれている | 綴りで引く（辿った記録があるか） | 記録どおり |
| 注釈が省かれている | 引かない | **「測れない」** |

**省ける位置は値の型 1 つではない。** 既定値つきの引数も注釈を省けるので、**引数ごとに**
持つ（Issue #200）。チャンクにつき 1 つの真偽へ畳むと、**既定値つきの引数が 1 つあるだけで、
注釈を書いてある引数と戻り値までまとめて測れない側へ落ちる**（同じ Issue の案 1。実コーパス
（rxjs 7.8.1 の `src`）で `Normalized` を 4 件失い、塞げたのは 0 件）。

**引数の対応は添字で取る。** `syntax::type_structure` の `Callable::parameter_type_names` も
ソースの引数リストも順序を持つので、**どの出現が書かれていないか**を位置で言える
（戻り値・型引数にこの鍵は無い）。**揃わなければ引数の位置すべてを省かれた扱いへ倒し**、
理由を分ける（上の表の 3 行目）。倒れる向きは偽陰性で、同じ実コーパスでは
`Normalized` が 314 件のまま変わらない。

**その位置に型名が残るかは、差し込む前の綴りで数える**（`semantics::type_signature` の
`spelled_annotatable_position_names_of`）。**差し込みも綴りで引く**ので、引数に書かれた
エイリアスの右辺が**同じ綴りの、推論された戻り値にも入る**。差し込んだ後で数えると
開かれた側が型名として残らず、**エイリアス越しに同じ偽陽性が通る**。

**外側の型が綴りを決めるのは、型を言い切る包みと代入先の注釈だけ**（`syntax::chunk` の
`TYPE_ASSERTION_KINDS`）。`as` / `<T>x` は書かれた型がそのまま hover の綴りになるが、
**`satisfies` は照らし合わせるだけで推論された型を残す**ので「書かれている」に数えない。
値を通すだけの包み（`syntax::tree` の `TRANSPARENT_EXPRESSION_KINDS`）をそのまま流用すると、
**型を言い切らない包みが混じる**。

**倒れる向きは偽陰性。** 推論された戻り値が引数と**同じ型**を指していても、指す先が同じかは
確かめられないので測れない側へ落ちる。実コーパス（rxjs 7.8.1 の `src`、尋ねた 517 チャンク）で
測ると、この形で `Normalized` を失うのは **2 件（0.4%）**（316 → 314）。

**キーワードの型と、そのシグネチャが束縛した型変数はここに数えない。** どこで書かれても
同じ型を指す / 辿る相手が居ないので、数えると**戻り値が `void` の関数と、注釈を省いた
ジェネリック関数がまとめて測れない側へ落ちる**（下の「束縛された型変数は…」と同じ理由）。

**Why not（同じ綴りが 2 回以上現れたら測れないにする）**: 出どころを持たずに済むが、
`(a: User, b: User) => User` のように**全部が同じ記号**の、注釈を書いてある普通の
シグネチャまで測れなくなる。

**Why not（hover の綴りの出現とソースの型名の位置を突き合わせる）**: **hover の綴りは
書き換えられている**（エイリアスが開かれ、接頭辞が付く）ので、綴りの中の位置どうしを
突き合わせる鍵は無い（#187 の案 2）。**引数だけは並びが鍵になる**ので、そこは上のとおり
添字で取る（#200）。

**4 行目に入るのは、型名のノードにならない綴り。** 値の名前（`typeof localValue`）・
オブジェクト型の計算されたキー（`{ [key]: string }`）・モジュールの指定子
（`import("./local").T`）・`this` 型で、どれも `syntax::type_reference` が集める対象に
ならないので上の 3 行のどれにも入らない。だが**指す先は書いた人の位置で決まる**ので、
綴りのまま比べると**別々のファイルの構造の違う値が単一化可能に出る**（偽陽性）。
見分けるのは `syntax::type_spelling` の `names_only_types`。

**そのシグネチャ自身の引数を指す `typeof x` はここに入らない。** どこに書かれていても
同じ引数を指すので、**辿る相手が居ない**（下の「束縛された型変数は…」と同じ理由）。
束縛を運ぶのは `syntax::type_structure` の `Callable::bound_value_names` で、
比較に残る形には持ち込まない（引数の名前は型を変えないので、残すと
**名前が違うだけの 2 つが別の構造になる**）。

**見るのは綴りのまま持つ部分だけ**（`syntax::type_structure` の
`Callable::names_only_types`）。分解できた部分は型が書かれる場所だけを歩いて組み立てた形で、
そこに残る綴りは型名なので、上の 3 行が答える。

**Why not（比較に残る綴り全体で見る）**: 綴り全体を 1 度読んでも同じ答えは出るが、
**分解できた部分の答えは上の 3 行が既に出している**。同じ問いに 2 つの経路で答えると、
片方だけが新しい形に追随したときに食い違う。

**Why not（型名として数えられないものを落として、綴りのまま比べる）**: `Unifiable` は
「重なることを確かめた」という答えで、**尋ねる位置を作れなかったことはそこに残らない**。
実コーパス（rxjs 7.8.1 の `src`）で測ると、比較に使えるシグネチャ 321 件のうち
5 件（1.6%）がこの行に当たり、5 件とも `typeof` の後ろの値の名前だった。

**束縛された型変数は「尋ねていない」に数えない。** `<T>(x: T) => T` の `T` は
このシグネチャの中でだけ意味を持ち、**辿る相手が居ない**。記録が無いのは当たり前なので、
数えると**ジェネリック関数がまとめて測れない側へ落ちる**
（`docs/dryguard-plan.md`「Stage 2」の「ジェネリクスは単一化を試みる」とぶつかる）。
外すのは比較に残る綴りを数える側（`syntax::type_structure` の `Callable::type_names`）で、
**外側のスコープが束縛した型変数は外さない**（TypeScript ではそのシグネチャからは辿れないので、
落とすと別のファイルの同じ綴りと重なる）。**Rust のメソッドは直接囲む impl のヘッダーも
運ぶ**ので、その型変数をメソッド自身とは別の名前空間で付け替える。個数も別々に比べ、
impl の変数とメソッドの変数が引数・戻り値で入れ替わった形を同一視しない。

**Rust の Self は直接囲む impl の対象型へ置き換える。** `self` / `&self` / `&mut self` は
その型の値 / 参照 / 可変参照にし、`mut self` の束縛の可変性は落とす。
対象型・impl の inline / where 境界・実装トレイトは impl のスコープで読む。
メソッドの型変数が同名の型・トレイトを shadow しても、impl 側の意味を変えない。
hover が `// Bounds from impl:` 以降に足す境界はソースの impl から読み直す。
問い合わせ位置も実ソースから採り、内側の自由関数には impl の文脈を渡さない。

**Self を含む関連型は、上の展開条件に当たるものだけを開く。** 当たらないものは理由付きで
測れない。impl が無い Self は `SiteDependentSpelling` のままで、const generics を持つ
impl は読み取り不可。型エイリアスは上記の既存の展開条件を保つ。

- **どの段で止まったかでは分けない。** 段で分けると、同じ「測れない」が
  typeDefinition・ファイルの読み込み・宣言の位置の hover に散り、
  **同じ対処を要する欠けが別々のバリアントになる**
- **理由は落とさない。** 「測れない」に畳むのは判定への効き方だけで、
  **利用者が次に何をするか**（サーバを替える / ファイルを読めるようにする /
  dryguard 側の穴）は理由が持つ（`semantics::resolved_type::UnopenedReason`）

**Why not（開けなかった型名があればシグネチャごと測れないにする）**: 比較に残らない綴りの
型名でも測れないになる。関数の名前が型名と同じ綴りで型引数を取ると
（`function Amount<T>(…)`）、**比較には残らない綴りを根拠に測れないと答える**ことになる。

**Why not（開けなかった型名を落とし、綴りのまま比べる）**: `NotUnifiable` は
「重ならないことを確かめた」という答えで、**開けなかったことはそこに残らない**。
`--explain` を読んでも、確かめた結果なのか確かめられなかったのかを区別できない。

**Why not（尋ねていない型名も綴りのまま比べる）**: 同じ理由が `Unifiable` の側にも要る。
別々のファイルが同じ綴りで構造の違う型を宣言していると、**宣言の場所が付かないまま綴りが
一致して単一化可能に出る**（偽陽性）。実コーパス（rxjs 7.8.1 の `src`）で測ると、
比較に使えるシグネチャ 360 件のうち 40 件（11.1%）がこれに当たる。

**Why not（辿った記録が無い型名があればシグネチャごと測れないにする＝束縛された型変数も
数える）**: 同じ実コーパスで 142 件（39.4%）が測れない側へ落ち、**そのうち 79 件は
型変数だけが理由**だった。

**コンストラクタが囲むクラスから受け取る型名は「尋ねていない」に当たらない。** hover は
`constructor Box<T extends Shape>(value: T): Box<T>` と綴るが、そこに載る
**クラスの名前（`Box`）も、クラスが宣言した型変数の制約・既定の型（`Shape`）も、
囲むクラスの宣言に書かれている**ので、尋ねる位置はそこに作れる（`syntax::type_reference` の
`constructed_class_references_of`。**2 つとも集める** — 名前だけにすると、制約を付けた
ジェネリッククラスのコンストラクタが測れない側へ残る）。

集める相手をそこまで広げないと、**収集対象の注釈に同じクラス名が現れないコンストラクタ**が
測れない側へ落ちる（同じ実コーパスで 23 件）。しかも**コンストラクタに戻り値の注釈は
書けない**ので、`--explain` が出す直し先が存在しないものになる。

**だから値の型は「書かれている」側で数える。** 戻り値を注釈できないのは setter も同じだが、
あちらは**受け取る引数の型**が hover の綴りになるので、引数の注釈の有無で決める
（`syntax::chunk` の `value_type_annotation_of`）。戻り値の注釈が無いことだけを根拠に
倒すと、**注釈を書いてある setter とすべてのコンストラクタがまとめて測れない側へ落ちる**。

## ファイル単位で決まる答えをチャンク単位で問い合わせない

`pipeline` が `semantics` / `lsp` へ問い合わせを組み立てるとき、**答えがチャンクではなく
ファイル（またはプロジェクト）について決まる**ものは、候補チャンクごとに呼ばない。
1 ファイルから N 個のチャンクを切り出すと、同じ答えを N 回問い合わせることになる
（`asked_paths_of` の `project marker` 探索・`AskedMembership::ask` が確かめる
`project membership` がどちらもこの形だった。pr-155 指摘 8・pr-158 指摘 8。
どちらも「その族に対応する分類が語彙に無い」と書いており、pr-158 側は
pr-155 と同じ形だと自己申告している）。

**`caller domain` のようにチャンク（シンボルの位置）ごとに答えが変わりうる問い合わせは
対象外。** 同じファイルの別の関数は参照元が別なので、ファイル単位へ畳むと答えが壊れる
（`asked_scan_semantics_of` は今も `caller domain` をチャンクごとに尋ねており、
`project membership` だけをファイルごとに 1 回へ畳んでいる）。

**呼ぶ前に、その問い合わせの答えが何に対して一意かを確認する。** ファイル単位なら
ファイルへ、プロジェクト単位ならプロジェクトへキーを揃えて 1 回だけ呼び、
結果を同じキーを持つチャンクへ配る。

| NG | OK |
|---|---|
| チャンクごとに `is_file` で祖先を辿り `project marker` を探す | ファイルごとに 1 回だけ辿り、同じファイルのチャンクへ配る |
| チャンクごとに `project membership` を尋ねる | ファイルごとに 1 回だけ尋ね、同じファイルのチャンクへ配る |

**Why**: LSP への問い合わせは同期的な往復を伴うプロセス外呼び出しで、
`project marker` 探索も印が無い木では毎回ファイルシステムの根まで辿る。
候補チャンク数はファイル数より多いのが通常なので、チャンク単位に据え置くと
候補が増えるたびに無駄な往復が線形に増える。

## Rust の参照元のテスト範囲

参照元のテスト範囲は `syntax::rust_test_scope` がソースだけから取り出す。
`semantics::caller_domain` が `codebase::source_of` でファイルを読み、その結果を渡して
参照位置を照合し、残った参照をドメインへまとめる。`pipeline` は compare / scan ごとに
`ReferenceSources` を共有する。読み込みと解析は参照元ファイルごとに一度で、
`syntax` に I/O、`pipeline` に構文判別を持ち込まない。

**除外はドメイン宣言の照合より先。** テスト内にしかない参照元が曖昧な宣言に当たっても、
本番の分布には影響しない。Rust ソースの読み取り・構文解析・位置の照合に失敗したときは
その理由を運び、読めた分だけで数えない。除外後に参照がなければ `NoReferences` とする。

## モジュールの公開 API

- モジュールは `mod.rs` ではなく `<名前>.rs` + 必要なら同名フォルダで構成する
- `pub` は最小限にする。**モジュール外から触る必要があるものだけ** `pub` にする
- モジュールの内部構造へ外から直接触らない（`pub(crate)` で段階を作る）

## lib と bin を分ける

`src/lib.rs` が本体で、`src/main.rs` は引数を受けて呼ぶだけ。

**Why**: bin だけの構成だと、テストからしか使われていない公開 API が `dead_code` になる。
`#[allow(dead_code)]` で黙らせるのは `rules/coding.md`「lint 抑制を足さない」に反するので、
構成のほうを合わせる。統合テスト（`tests/`）が書けるようになる利点もある。
