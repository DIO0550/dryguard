# tests/corpus — Phase 0 の検証用 TS コーパス

`harness/phase0/verify.sh` を当てる対象。受注オペレーションの小さなバックエンドを想定した
TypeScript で、5 ドメイン（`billing` / `inventory` / `shipping` / `notification` / `analytics`）と
共有ユーティリティ（`shared`）に 19 ファイル・47 関数を置いてある。

## `tests/fixtures` と何が違うか

**書いた順番が違う。**

| | 書いた順番 | 何に使えるか |
|---|---|---|
| `tests/fixtures` | 計画の出力イメージ（`billing/discount.ts` ↔ `inventory/reorder.ts` が `DO-NOT-EXTRACT`）を**先に決めて**、それが出るコードを書いた | `report` / `compare` の回帰テスト |
| `tests/corpus`（ここ） | 「よくある業務アプリ」として**先に書いて**、判定は後から見た | 判定の傾向を見る |

fixtures は答えが先にあるので、これで頻度を数えても循環する。corpus はその循環を避けるために
順番を逆にしてある。

## それでも頻度の証拠にはならない

**このコーパスは我々が書いたものなので、「実際のコードベースに偶発的重複がどのくらいの
頻度で存在するか」の答えにはならない。** 何をどれだけ書くかを我々が決めている以上、
出てくる頻度も我々が決めている。

Issue #17 のゲートのうち、このコーパスで答えられるのは**判定が納得できるかどうか**の側だけ。
頻度の側は、判定のことを考えずに書かれた実コードでしか測れない。

**それでも意味があるのは、判定の弱点が見えたため。** 見つかった 2 つ
（短い関数で構造類似度が過大に出る / `import` 集合がファイル単位なので希釈される）は
**アルゴリズムの性質であってコーパスの性質ではない**ので、どのコードベースに当てても同じように出る。
詳細は [Issue #17](https://github.com/DIO0550/dryguard/issues/17) のコメント。

## 書くときの約束

- **判定を先に決めない。** そのドメインに必要な処理として書き、判定は後から見る
- **`compare` を通すための細工をしない。** 実際のコードに現れない形（無意味に長い関数、
  わざと似せた 2 つ）を入れると、また循環する
- 足すときは、その言語で自然な書き方を混ぜる。現在は `export function` だけなので、
  **式本体のアロー関数（`const f = (x) => x + 1;`）とクラスのメソッドが 1 つも無い**。
  `harness/phase0/README.md` に書いた「種に上がらない関数がある」制限を、
  このコーパスは**まだ踏んでいない**（47 関数すべてが種に拾えている）

## ビルドしない

TypeScript のコンパイルもテスト実行もしない。**`compare` に読ませる入力であって、
動かすアプリケーションではない。** `tsconfig.json` も `package.json` も置かないのはこのため。

型としては整合させてある（`import` の解決先が実在する）。依存先の重なりを測る対象が
`import` 文なので、解決できない `import` を書くとシグナルのほうが壊れる。
