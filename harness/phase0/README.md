# Phase 0 の検証ハーネス

`docs/dryguard-plan.md`「Phase 0」のゲートを通すための足場。

> 実際のコードベースに「構造は似ているが依存ドメインが違うペア」は、
> 意味のある頻度で存在するのか？

## なぜプロダクトの外にあるか

`compare` は 2 箇所を名指しで受ける。頻度を数えるにはペアの列挙が要るが、
**列挙は `scan` の仕事で Phase 1 に置かれている**（`docs/dryguard-plan.md`）。

検証のために `scan` を先回りで生やすと、`src/cli.rs` が避けている
「受け取るだけで結果が出ないサブコマンド」を足すのと同じことになる。
ここは検証の足場であって、プロダクトの機能ではない。

**Why not（統合テストに置く）**: `tests/` は振る舞いの回帰を見る場所で、
落ちたら CI が止まる。こちらは対象リポジトリが手元にあるときだけ走らせる
一回きりの調査なので、常時走る検査に混ぜない。

## 使い方

```bash
bash harness/phase0/verify.sh <対象ディレクトリ> [出力先ディレクトリ]
```

出力先の既定は `harness/phase0/out/`（git 管理外）。

| ファイル | 中身 |
|---|---|
| `seeds.txt` | 集めた関数の位置（`file:line`） |
| `verdicts.txt` | ペアごとのラベル（タブ区切り） |
| `do-not-extract.txt` | `DO-NOT-EXTRACT` が出たペアの `--explain` 付き出力 |
| `unchunkable.txt` | チャンクを切り出せなかったペアと理由 |

ペア数が `DRYGUARD_MAX_PAIRS`（既定 200000）を超えたら**間引かずに止まる**。
黙って一部だけ回すと、出た件数が全体の何割なのかが読めなくなる。

## 関数の位置の集め方

`compare` は「その行を含む関数」を切り出すので、関数 1 つにつき 1 行あればよい。
種にする行の判定条件は `src/syntax/chunk.rs` の `is_function_header` に合わせてある。

**合わせてあるだけで、同じ実装ではない。** ずれた場合は切り出せない位置が種に混ざるが、
それは `compare` が `NoEnclosingFunction` で落として `unchunkable.txt` に出るので、
黙って取りこぼす形にはならない（`rules/testing.md`「フェイルオープンかつサイレント」を避ける）。

逆に、**種に出てこない関数は数からも漏れる。** 現在の `is_function_header` は
`{` で終わる行しか見ないので、式本体のアロー関数（`const f = (x) => x + 1;`）と
シグネチャが複数行にまたがる関数は対象外。頻度を読むときはこの取りこぼしを前提にする。

## 隣にあるもの

`chunk-unit-probe/` は、**ブロック単位まで落としたら何が拾えたか**を数える別の足場
（Issue #18）。`verify.sh` は `compare` を呼ぶため出てくるのが常に関数単位のペアで、
**関数の一部だけの重複を取りこぼしているか**はここでは数に出ない。

## 結果の残し方

検証の結果・当てたリポジトリ・出たペアの実例は、**Issue #17 のコメントに残す**
（`AGENTS.md`「実装の進め方」: Issue は判断の履歴）。`out/` は git に入れない。
