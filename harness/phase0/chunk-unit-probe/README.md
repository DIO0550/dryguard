# chunk-unit-probe — チャンクの単位を決めるための計測

「関数の一部だけが重複しているケースを、関数単位のチャンク化が取りこぼしているか」（偽陰性）を数える。
Issue #18（チャンクの単位を決める）の判断材料。

## `verify.sh` では測れない理由

`harness/phase0/verify.sh` は `compare` を呼ぶ。`compare` が切り出すのは**その行を含む関数**なので、
出てくるのは常に関数単位のペアになる。**取りこぼしは定義上そこに現れない。**

数えるには「ブロック単位まで落としたら何が拾えたか」を別に測るしかない。それがここ。

## 使い方

```bash
cargo run --manifest-path harness/phase0/chunk-unit-probe/Cargo.toml -- <対象ディレクトリ>
```

出力は 4 つ。

| 見出し | 中身 |
|---|---|
| 数えたもの | 関数・ブロックの件数と、それぞれを比較したときのペア数（単位を落としたときのコスト） |
| 閾値を超えたペア | 関数単位で超えた数と、ブロック単位で新たに増える数（増える候補の量） |
| 関数単位が取りこぼし、ブロック単位が拾うペア | **偽陰性の候補。** 関数ペアの位置とブロックの位置を両方出す |
| ブロックの大きさ | 行数・トークン数の分布。短い単位ほど構文語が集合を占める（#86）ので、単位を落とした影響を見る |

取りこぼしの候補に出た位置は、そのまま `compare <locA> <locB> --explain` に渡せる。

## なぜ別クレートか

**プロダクトに入れない理由**は `harness/phase0/README.md`「なぜプロダクトの外にあるか」と同じ。
ブロック単位のチャンク化を `syntax` に足すと、**単位を落とすかどうかを決めるために単位を落とした
実装が要る**という順序の逆転が起きる。ここは判断のための計測であって、機能ではない。

**それでもプロダクトのクレートに依存する**のは、類似度の測り方を同じにするため
（`TokenSet` と `Similarity` をそのまま使う）。別実装にすると、出た差が「単位の違い」なのか
「測り方の違い」なのかを読み分けられない。

**Why not（bash + `compare` で済ませる）**: `compare` は関数しか切り出さないので、
ブロックのトークン集合を作る手段が無い。

## 前提として引き受けた制限

- **CI（層 1）にも pre-push（層 2）にも入らない。** どちらもルートのパッケージだけを見る。
  この足場を常時の検査に入れると、一回きりの調査コードが恒久的なコストになる
  （`verify.sh` が bash で検査の外にあるのと同じ扱い）。**クレートの公開 API が変われば
  ビルドが落ちる**ので、走らせた回に黙って間違った数が出る形にはならない
- **関数として拾うノードの種別は `src/syntax/chunk.rs` の `CHUNK_KINDS` に合わせてあるだけ**で、
  同じ実装ではない。ずれたら関数の件数が `verify.sh` の種の件数と食い違うので、突き合わせれば気付ける
- **ブロックの種別はこちらで決めている**（`if` / `for` / `while` / `do` / `switch` / `try`）。
  実際にブロック単位へ落とすときに同じ切り方を採るとは限らない
