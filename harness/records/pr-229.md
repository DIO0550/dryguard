## ゴールと結果

Issue #34 のゴールは「`--format text|json` を実装し、JSON で判定結果を出せるようにする」で、
出すものとして 4 項目（ペアの位置 / ラベル / シグナルの値 / 理由と提案）が挙がっていた。
加えて「**text で出している情報が JSON で落ちないようにする**。逆に、JSON にだけ入れて
text から落とすものがあるなら、それも意図して決める」という条件が付いていた。

4 項目はすべて出した。**落とさない条件のほうは、text 側の関数を 1 つずつ読んで
突き合わせた**（`report.rs` の `text_of` / `scan_text_of` が出す行と、`json.rs` が出すキー）。

| text が出しているもの | JSON での出しかた |
|---|---|
| ラベル | `verdict`（`Verdict` の `Display` と同じ綴り） |
| 両側の位置 | `location_a` / `location_b` の `file` と `line` |
| シグナルの値と傾き | `reasons[].value` と `reasons[].lean` |
| 当てた閾値 | `reasons[].threshold`（モジュール距離だけ `separate_directory_steps`） |
| 測れなかった理由 | `value.status` と `value.reason` |
| 理由が持つ数値・綴り | `line` / `counted` / `found` / `project_markers` |
| 提案 | `suggestion`（text と同じ `suggestion_of` から組み立て） |
| 走査した量 | `walked` |
| 飛ばしたファイル・切り出せなかった関数 | `skipped_files` / `unchunkable` |

**意図して違えたものは 2 つ**で、どちらも PR 本文に書いた。

1. **類似度・重なりは丸めない値を出す**（text は小数第 2 位）。読む側が閾値との
   突き合わせをやり直せるほうを採った
2. **`walked` に候補ペアの数を入れない**（text は併記している）。`candidate_pairs` の
   要素数がそのままの答えで、同じ数を 2 箇所に置くと片方だけ直したときに食い違う

**ずれ**: 無し。ただし**読み取りが割れた点が 1 つあり、自分で決めて進めた**。
Issue 本文の「シグナルの値（`--explain` と同じ情報）」は (a)「JSON は常に全部出す」とも
(b)「JSON も `--explain` で増える」とも読める。(b) を採った理由は、(a) だと
`--format json --explain` と `--format json` が同じ出力になり、**`--explain` が JSON では
黙って効かなくなる**ため（`rules/coding.md`「まだ動かない選択肢を enum に並べない」が
避けている「指定が効いていないのか未対応なのか区別できない」と同じ形）。
Discord で質問して止めるほどの割れではないと判断し、選択肢と根拠を Issue #34 の
計画コメントに残したうえで進めた。

**残タスクは Issue #230 へ出した**（下の指摘 4）。

## 数えなかったレビュー指摘

### `reason_of` の `panic!` メッセージが「実際の失敗条件と逆」

`copilot-pull-request-reviewer` が Low severity で挙げた
（https://github.com/DIO0550/dryguard/pull/229#discussion_r4071667578 ）。
`let ... else` の `else` 節、つまり根拠が**見つからなかった**ときにだけ出るのに、
メッセージが「`{signal}` の根拠が出ている」になっている、という内容。

**成り立たないと判断した。** `grep -rn 'panic!("' src/ tests/` で既存の書き方を数え直すと、
**このリポジトリの `panic!` は「崩れた前提」を肯定形で書く**流儀で一貫している。

| 場所 | メッセージ | 出るとき |
|---|---|---|
| `src/lsp.rs:1122` | 呼び出し元のあるチャンクには参照元が返る | 返らなかったとき |
| `src/cli.rs:132` | compare を渡したので Compare になる | ならなかったとき |
| `src/report.rs:1075` | テストが渡す参照元は 1 件以上 | 0 件だったとき |

`reason_of` の「`{signal}` の根拠が出ている」も同じ形なので、ここだけ否定形にすると
流儀が割れる。doc の `# Panics` が書いているのは**いつ落ちるか**、メッセージが書いているのは
**何を前提にしていたか**で、役割が違う。理由をスレッドへ書いてから resolve した。

**記録としては `- 分類:` を立てない。** 欠陥でないものに分類を付けると、その分類の
再発数が実際より多く出て、「2 回以上で規約の抜け」の判断が壊れる。
