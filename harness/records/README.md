# harness/records — マージ後の評価記録

マージされた PR 1 本につき `pr-<番号>.md` を 1 ファイル置く
（例外は「[記録だけの PR には記録を作らない](#記録だけの-pr-には記録を作らない)」）。

## 何のためにあるか

`AGENTS.md`「規約の更新」は「ルールに書かれていない指摘が **2 回以上**出たら
規約の抜けとして扱う」と定めている。ここはその**回数を数えるための材料**。
指摘がレビューコメントに散っている限り横断して数えられないので、
分類タグを付けた形でマージのたびに 1 ファイル残す。

## `.claude/` の下には置かない

記録はマージのたびに必ず 1 ファイル増えるが、`.claude/` 配下への書き込みは編集のたびに
承認を求められる。記録を残すこと自体が目的なのに、毎回そこで人の手を止めるのは割に合わない。
読み書きの頻度が高い成果物はリポジトリの通常のフォルダに置く。

## 数え方

```bash
bash harness/records/count.sh
```

分類ごとに「**最後の介入以降**の再発数」「通算」「介入後の記録の本数」「前回置いた層」を出す。

**通算ではなく再発で判断する。** 通算は単調増加するので、介入が効いたかどうかを表さない。
再発を数えられるのは、介入した回の記録に次の行が入っているため。

```markdown
- 対策済: `naming-mismatch` 層=rules at pr-42
```

## 書き方

形式・層の語彙・分類の語彙は [`TEMPLATE.md`](TEMPLATE.md)。

- 指摘 1 件 = 1 ブロック（まとめない）
- **指摘 0 件の回も記録を残す**（「順調だった」もデータ）
- **過去の記録は書き換えない。** 判断が変わったら新しい記録に書く
- **推測で埋めない。** 実際のレビューコメント・CI の出力に当たる

## 記録だけの PR には記録を作らない

**この `harness/records/` 配下だけを変える PR は、それ自身の `pr-<番号>.md` を作らない。**
その回にレビュー指摘が付いたら、**次に実装が入る PR の記録へ併記する**
（どの PR の回のものかを書く。1 段ずれるので、書かないと出どころが辿れない）。

**Why**: 記録を入れる PR にも記録が要るとすると、**その PR にもまた記録が要る**。
実際 pr-107 を入れた回には 15 件の指摘が付いており、そこで記録を作れば同じことが次にも起きる。

**Why not（指摘 0 件の回で止める）**: 「0 件なら次は書かない」でも連鎖は止まるが、
**止まるかどうかが指摘の件数で決まる**ので、書き終えるまで分からない。
**範囲で決めるほうが、着手する前に予測できる。**

**Why not（記録だけの PR の指摘を捨てる）**: 上の 15 件は**どれも記録の正確さに関するもの**で、
コードの欠陥は 1 件も無い（数の引き継ぎ・同じ数を 2 箇所に書く・数える範囲の書き落とし・
対策の側で分類する、など複数の形に分かれる。内訳は `pr-110.md`）。
**規約の抜けを数える材料としてはむしろ濃い**ので、連鎖を止めるために捨てる必要は無い。

## 記録は溜まり始めている

本数は `ls harness/records/pr-*.md | wc -l` で数える（**この README には書かない**。
マージのたびに増える数を 2 箇所に置くと、片方だけ古くなる）。

`AGENTS.md`「実装を始める前に」には、記録から **2 回以上出た指摘だけ**が上がっている。
**数えるのと、規約やフックへ手を入れるのは別の回に行う。** 記録を書く回は材料を残すところまで。
