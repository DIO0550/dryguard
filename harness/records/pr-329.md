## ゴールと結果

Issue #317 のゴールは次の 3 つだった。

- 入れ子の投影（`Self::Item::Nested` / `<<Self as Trait>::Item as Other>::Out`）
- 関連型 RHS の `Self`（`type Item = Self` / `(Self, T)`）
- RHS の中の再帰投影

着手時にタスクを分割し、この PR は「RHS の単独の `Self`」に絞った。入れ子の投影・RHS の中の投影と、
`rules/architecture.md` が #317 に紐づけていた短縮形（inherent impl の `Self::Item`）は #327 に分けた
（理由は Issue #317 のコメント「タスクの分割」）。

絞った範囲は達成した。

- 直接囲む trait impl の経路（#303）と、別の impl を選ぶ経路（#310）の両方で、RHS の `Self` を
  使用側の impl の対象型として展開する
- 既存の統合テストの `unsupported`（`type Item = Self`）は `UnopenableAssociatedType` から
  `Normalized` に変わった（`itself` に改名）
- RHS の中の投影（`type Again = Self::Item`）は変更前と同じ `UnresolvedAssociatedType` のまま

- push した head は `d700cd8` の 1 つだけ。Rust のワークフローは成功した。PR body のワークフローは

## 指摘

### 1. receiver の無い inherent impl で、対象型の型名を尋ねていないことを計画が見落とした

- 分類: `plan-case-omission`
- 出どころ: 自己修正（計画の検証 High-1）
- 内容: 計画は hover 側で RHS の `Self` を `self_spelling` で綴るだけだった。ソース側の
  `type_references_of` が impl の対象型を歩くのは、実装 trait の境界・`self` 引数・単独の `Self` の
  ときだけ。receiver の無い inherent impl のメソッドは対象型を歩かないので、`Holder` を辿った記録が
  無く `UntracedTypeName` に倒れる。ソース側でも `Self` を含む投影を歩くときに対象型を歩く形を

### 2. RHS の中の投影の理由を、コードを確かめずに `UnopenableAssociatedType` と置いた
