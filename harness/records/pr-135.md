# PR #135 [Phase 2] 同じ綴りで別の記号を指す型を、定義の場所で見分ける

- マージ日: 2026-09-02
- 関連 Issue: #131
- 差分規模: 9 ファイル / +401 -34

## ゴールと結果

**ゴール**: 同じ綴りで別の記号を指す 2 つの型（`billing/User` と `report/User`）を
単一化不能と判定できるようにする。併せて #116 の「決めること」にあった
「解決した型を別ドメインの型として扱えるか」に答える。

**結果**: 達成した。`TypeSignature` に「比較に残る型の綴りに現れる型名ごとの宣言の場所」を
持たせ、等値に含めた。**別ドメインの型を独立したシグナルにはしていない。**
`docs/dryguard-plan.md` の Stage 3 の表が「単一化不能 / 別ドメインの型」を同じ型シグネチャの
シグナルの中に並べているので、そこへ畳んだ（`rules/architecture.md`「判定は 1 箇所にだけ置く」）。

**計画の前提が 1 つ外れていた（良い方向に）。** Issue は `typeDefinition` を新たに送る話として
書かれていたが、**#116 の `type_declarations_of` が既にチャンクの型名すべてへ送っており**、
`open_declaring_documents` も宣言のあるファイルを開かせていた。`resolved_types_of` が
右辺の綴りだけを取り出すので、`interface` / `class` では `DeclarationSite` が誰にも
見られずに消えていただけだった。結果として **LSP の往復は 1 回も増えず**、Issue の
「決めること」3 つ目（組み込み・外部の型で問い合わせが増える）は前提ごと消えた。

**レビューは 2 巡。** Codex 1 巡で 3 件（P1 1 件 / P2 2 件）、修正後の Codex 再レビューと
Copilot レビューはどちらも指摘 0 件。CI は 2 回とも 1 発で通った。

- 出どころ: レビュー（Codex 1 巡目・P1）

  `T extends U ? Local : number` の `Local` の後ろ ` : number` が `:` から始まる綴りとして
  扱われ、メンバー名として読み飛ばされていた。**この PR が消したかった偽陽性が
  そのまま残る**。印を名前の直後だけで見る形に直した
- 既存ルール: なし
- 次にどう防ぐか: 今回は記録のみ

  **pr-132 の指摘 28 と同じ根**（当時は「条件型の真の枝で差し込みが止まる」として
  #133 へ積んだもの）。**この PR が同じ述語を新しい用途（綴りに残った名前を数える）から

  （`VETTED_MEMBER_MARKERS`）だけで、**差し込む側（`Placement::names_a_member` /
  `MEMBER_MARKERS`）は今も `trim_start` している**ので、#133 の項目は残っている

### 2. 正規化で落ちる関数の名前を型名として数える

- 分類: `なし`
- 出どころ: レビュー（Codex 1 巡目・P2）
- 内容: 宣言を引く相手を、差し込んだ後のシグネチャ全体から探していた。そこには
  正規化で落ちる関数の名前が含まれる。`function Amount<T>(value: Amount): T` では
  差し込みで `Amount` が消えた後も前置きに `Amount<` が残り、`<` は印として数えない側に
  置いてあるので拾われる。**比較には残らない綴りを根拠に別物と答える**（偽陰性）。
  型が書かれる場所（型変数の制約と既定の型・引数の型・戻り値の型）だけを渡す形に直した
- 既存ルール: なし
- 次にどう防ぐか: 今回は記録のみ

  **指摘 1 と同じく「同じ定数を、その doc が書いている前提が成り立たない場所で使い回した」形**
  （pr-132 の指摘 30 と同型）。`VETTED_MEMBER_MARKERS` は開いた後の綴りを検証する前提で
  作られており、**シグネチャ全体の綴り**を渡す用途は想定に無かった

### 3. テストだけが使う組み立ての口が公開 API に出ている

- 分類: `module-api`
- 出どころ: レビュー（Codex 1 巡目・P2）
- 内容: `DeclarationSite::new` を `pub` で足したが、呼び出し元は `src/test_support.rs`
  だけだった。宣言の場所は必ずサーバの応答から作られるべきもので、組み立てる口を
  公開したままにすると検証を通っていない場所がクレートの外から作れる
- 既存ルール: rules/architecture.md「モジュールの公開 API」（`pub` は最小限にする）
- 次にどう防ぐか: 今回は記録のみ（既存ルールに書かれており、読み落としの側）

  **指摘どおり `pub(crate)` にするだけでは通らなかった。** `test_support` は
  `#[cfg(test)]` なので本番のビルドで呼び出し元が 0 になり `dead_code` で clippy が落ちる。
  `#[allow(dead_code)]` は `rules/coding.md`「lint 抑制を足さない」に反するので、
  `#[cfg(test)] pub(crate)` にした。**この形はこのリポジトリで初めて
  （既存の `#[cfg(test)]` は `mod tests` と `mod test_support` だけ）**

## うまくいったこと

- **計画の入力を数え直した。** `AGENTS.md`「実装を始める前に」の 1 項目め。Issue が
  「`typeDefinition` を足す」話として書いていた前提を、実装前に `type_declarations_of` /
  `open_declaring_documents` を読んで確かめたところ、**問い合わせは既に全部送られていた**。
  「決めること」3 つ目が前提ごと消え、差分が「捨てていた材料を持ち回すだけ」に縮んだ
- **差し込みで消えた名前を持ち回さない形を、実装の前に決めた。** ここを外すと
  `billing/Amount = number` と `report/Amount = number` が宣言の場所の違いで別物になり、
  **#116 が直した偽陰性が戻る**。回帰テストも同時に置いた
- **ミューテーション確認を 4 回回した。** `remaining_declarations_of` を「空を返す」形と
  「全部返す」形に壊して落ちるテストを数え、レビュー修正の 2 件も**直す前に落ちること**を
  先に確かめた。実サーバのテストが指摘前の形で落ちることも確認した
- **対照を必ず 1 件置いた**（`rules/testing.md`「『出ない』を確かめるときは、対照を 1 件置く」）。
  「同じ綴りで別の記号 → 単一化不能」に対して「輸入した同じ記号 → 単一化可能」を、
  モジュール内テストと実サーバのテストの両方に置いた。**綴りが同じことを拒んでいるのではなく、
  指している記号が別なことを拒んでいる**が、これで初めてテストから読める
- **コミットを指摘ごとに分けた。** 差分が 1 ファイルに混ざっていたので、いったん
  `git checkout` で戻して 1 件目だけ書き直し、**中間状態で `cargo test` / `clippy` が通ること**を
  確かめてからコミットした
