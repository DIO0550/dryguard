## 指摘

### 1. 注釈全体を占めるエイリアスを開けないと、理由が `UnreadableSignature` に化ける

- 分類: `plan`
- 出どころ: レビュー（Codex P2）
- 内容: `const halveAmount: Scaling` は `Scaling` を開かないと引数リストが現れず
  `SplitSignature` が割れない。正規化に入れないまま `UnreadableSignature` へ落ちるので、
  同じコミットで足した `UnopenedReason` が捨てられていた。
  **「測れない」の理由が「その型名を開けるようにする」から「dryguard 側の穴」へ入れ替わる。**
  計画では「黙って落としている箇所」を `grep -n "continue"` で数えたが、
  **この経路は `continue` ではなく早期 `None` return** なので、その数え方では拾えなかった
- 既存ルール: `AGENTS.md`「実装を始める前に」（完了条件を grep 等で機械的に確かめられる
  形に落とし、自分で数え直す）
- 次にどう防ぐか: 今回は記録のみ。**「完了条件を機械的に確かめる」自体は行っており、
  誤ったのは検査式の当て先**（`continue` を数えたが、答えを出す経路を数えるべきだった）。
  同じ形が次に出たら、既存項目の表現を直すか層を上げるかを判断する

### 2. 開けないエイリアスを、エイリアスでない宣言と同じに落としていた

- 分類: `plan`
- 出どころ: レビュー（Codex P2）
- 内容: `resolved_type_of` の `None` が 3 つの別々のことを畳んでいた。
  `interface` / `class` に右辺が無いのは**開く先が無いというサーバの答え**だが、
  `type Box<T> = { value: T }` は**サーバが右辺を返しているのに dryguard が差し込めない**。
  同じ `None` で落としていたため、確かめていない `NotUnifiable` が残っていた。
  **計画コメントでは「この枝は落として正しい」と明示的に書いており、
  `interface` / `class` の場合しか見ていなかった**
- 既存ルール: `AGENTS.md`「実装を始める前に」（計画の入力を鵜呑みにしない）
- 次にどう防ぐか: 今回は記録のみ。指摘 1 と同じ形（同じ回に 2 件）なので、
  次の回に**同じ形が出るか**を見る

### 3. 計画コメントに載せた grep 出力が、実際の出力と食い違っていた

- 分類: `unverified-claim`
- 出どころ: 自己修正
- 内容: Issue の実装計画コメントに `grep -n "continue"` の出力を載せたが、
  **注記を付け足した編集済みの出力**で、`src/pipeline.rs` の一致も 5 件と書いた実際は 7 件だった。
  同じコメントの `docs/dryguard-plan.md` の grep も、**走らせたパターンと書いたパターンが
  違って**おり、「一致 1 件」と書いた実際の一致は 0 件。
  どちらも結論は変わらなかったが、根拠として出した数が誤っていた。
  **書いた直後に一次情報から出し直して自分で見つけ、[訂正コメント](https://github.com/DIO0550/dryguard/issues/144#issuecomment-5548263024)を残した**
- 既存ルール: `AGENTS.md`「記録・PR 本文に数値や主張を書く前に」
- 次にどう防ぐか: 今回は記録のみ。**規約は既にあり、それに従って自己検出できている**
  （書いた後ではあるが、提出前に直っている）。出し直しの位置を「書いた直後」から
  「書く前」へ動かせるかは、同じ形が再発したときに考える

## 手戻り

- **設計の形を実装前に 5 回変えた。** 宣言 / 解決後の綴り / 開けなかった型名の 3 つを
  どこに持たせるかで、`ResolvedTypes` に入れる → 引数を 4 つにする → 構造体 2 つに分ける →
  タプルで返す → `TracedTypeNames` 1 つにまとめる、と往復した。決め手になったのは
  `normalized_outcome_of` の引数を 3 つ以内に収めることと、`rules/naming.md`
  「名前と実体を一致させる」（`ResolvedTypes` に開けなかった理由を入れると語と実体がずれる）
- **`cargo fmt --check` が 1 度落ちた。** テスト名が長すぎて rustfmt が `fn ...()\n    {` の形に
  割ろうとしたため、テスト名を短くした（`..._a_signature_keeping_two_unopened_type_names_answers_by_name_order`
  → `..._two_unopened_type_names_answers_by_name_order`）
- **レビュー指摘 2 の修正で、当て先が 1 つ増えた。** 型引数を取るエイリアスが比較に残る綴りに
  現れるペアは `NotUnifiable` ではなく「測れない」になる。軸に従った結果だが、
  実コードで `Partial` / `Record` を使うシグネチャが多いと REVIEW が増えうる。
  **どれくらい増えるかは測っていない**ので、[Issue に次に測りたいこととして残した](https://github.com/DIO0550/dryguard/issues/144#issuecomment-5548445067)

## うまくいったこと

- **軸の両方向を壊して確かめた。** `rules/testing.md`「迷ったら、その 1 件だけ実装を壊して
  走らせる」に沿って、判定を消す（2 件落ちる）／比較に残る綴りの絞り込みを外す（3 件落ちる）
  の両方を実行した。レビュー指摘 1 の修正でも同じことをしている（それぞれ 1 件落ちる）。
  **「出ない」側のテストが何も守っていない状態を、頭ではなく実行で否定できた**
- **レビュー指摘の影響範囲を、推測ではなく grep で確かめた。** 指摘 2 の修正が既存の LSP
  テストを壊さないことを `grep -rn "type [A-Za-z_]*<" tests/fixtures tests/corpus`（一致 0 件）で
  先に確かめ、CI の実サーバ実行（21 件通過）で裏が取れた
- **CI が 3 コミットとも実サーバのテストを通した。** `typescript-language-server` が
  実行環境に無く手元では 21 件すべて `ignored` になるが、`cargo test -- --ignored` が
  無条件に走る層 1 があるので、**LSP を通る経路を最も変えた回でも検証が空にならなかった**

## 実行環境のメモ

- **層 3（Claude Code hooks）は判定できなかった。** `echo hook-canary` は deny されずに

  「フックが発火しない環境」とは断定できない

  `{"plugins": {}}` で、`rust-rules-plugin@d-market-rust` の `coding-standards` / `tdd` /
  `testing` スキルは読めていない。各 `rules/*.md` の「前提として守るもの」の箇条書きだけを
  頼りにした
- **`typescript-language-server` が無い。** `tests/semantics.rs` の 21 件は手元では
  すべて `ignored`。実サーバの検証は CI の `cargo test -- --ignored` が担った

- テスト数は `655 → 662`（`grep -rc 'fn test_' src/ tests/` を PR のベース `c79f936` と
