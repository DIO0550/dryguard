### 測った結果（#173 のコメントに全文）

rxjs 7.8.1 の `src`（251 ファイル / 961 チャンク / 尋ねた 517）で、`TypeSignatureOutcome` が
`Normalized` になるのは 360 件。案 A をレビューの文言どおり入れると 142 件（39.4%）が
「測れない」へ動く。

**このうち 79 件は推論された型名ではなく型変数が原因だった。** `Callable::type_names()` は
型変数を付け替える前に数えるので `<T>(x: T) => T` が `{"T"}` を返す一方、
`type_references_of` は束縛された名前を意図的に集めない（辿る相手が居ない）ため、
「辿った記録が無い型名」に入ってしまう。束縛した型変数を除く案（#173 で案 A' として提示）
なら 63 件（17.5%）に収まる。

**この材料は `docs/dryguard-plan.md`「Stage 2」を読んで初めて決め手になった** —
「ジェネリクスは単一化を試みる」と正面からぶつかる。

### 1. 「集められなかった型名」が、このモジュールが持たないと明言している状態を指していた

- 分類: `naming-vocabulary`
- 出どころ: レビュー（Codex P2）
- 内容: 足した doc に「**集められなかった型名**は綴りのまま比べられ」と書いた。だが
  **同じファイルの `type_references_of` の doc**（マージ後の木で
  `src/syntax/type_reference.rs:102-103`）が
  「**空は「書かれていない」。**…集められなかったという状態は無い（構文木からは必ず採れる）」と
  書いており、**1 つのファイルの中で語彙が食い違っていた**。推論された型名はそもそも
  `type reference` ではないので「集め損ねた」ものではなく、集める側を直せば拾えるかのように
  読めてしまう（直前の文が「集める側を変えても動かない」と正しく書いているのと矛盾する）
- 既存ルール: rules/naming.md「このツールの語彙を固定する」
- 次にどう防ぐか: 今回は記録のみ。**規約はあり、守れていなかった回**。とくに
  「同じファイルの別の doc が既にその語を否定していないか」を見ていなかった

### 2. 「開けなかった型名が「測れない」へ倒れる」の参照先が別の型で、限定も落ちていた

- 分類: `comment-mismatch`
- 出どころ: レビュー（Codex P2）
- 内容: 2 つの誤り。(a) 参照先を `semantics::resolved_type` の `UnopenedTypeName` と
  書いたが、これは**型名 1 つと開けなかった理由の記録**（`resolved_type.rs:127`）で、
  「測れない」という答えは `semantics::type_signature` の
  `TypeSignatureOutcome::UnopenedTypeName`（`type_signature.rs:130`）のほう。
  **同名の型が 2 つあり、doc から追うと別の型に行き着く**。(b) `single_outcome_of` は
  `remaining_type_names` に現れた型名しか `unopened_reason_of` に掛けないので、
  開けなかった型名がすべて「測れない」になるわけではない
  （`rules/architecture.md`「どこまでを「取れなかった」に数えるか」の表のとおり）。
  限定を落としたまま書いたので、推論された型名との対比を過大に述べていた
- 既存ルール: rules/coding.md「コメントは doc と Why / Why not に絞る」
- 次にどう防ぐか: 今回は記録のみ。**doc に型名を書くときに、その綴りの定義が
  リポジトリに 1 つしか無いかを確かめていなかった**。`UnopenedTypeName` の定義は **3 つ** —
  `resolved_type.rs:127` の struct、`type_signature.rs:130` の
  `TypeSignatureOutcome` のバリアント、`classification/signal.rs:190` の
  `TypeSignatureMatch` のバリアント。綴り自体は `src/` の 7 ファイル・39 行に現れる
  （**PR #185 をマージした木 `2cf449d` で数えた**。この記録を入れる PR 自身が
  コンストラクタの手当てで綴りを増やすので、どの木で数えたかを書かないと古くなる）

## 手戻り

**1 巡目の doc に、レビュー指摘 2 件 = 誤り 3 つを入れた。** 指摘 1 が 1 つ、
指摘 2 が (a) 参照先の型違い と (b) 限定の落ちの 2 つを含む。直す対象が
「doc の 1 文が事実と違う」ことだったのに、**書き換えた側にも事実と違う記述を入れた**。
差分 8 行に対して誤り 3 つは密度が高い。原因は、書いた内容を既存の doc と
`grep` で突き合わせなかったこと。

**スコープは着手直後に変えた（手戻りではない）。** Issue を読んだ時点で判断待ちと分かったので、
実装に入らず「測る」→「どの案でも誤りな doc だけ直す」に絞った。コードは書いていないので
捨てた作業は無い。

**計測用のプローブは出荷しないと決めた。** `harness/` のクレートとして出すには
`semantics::type_signature` と `pipeline` の private を外へ出すことになり、
`rules/architecture.md`「`pub` は最小限にする」とぶつかる。プロダクトと同じ経路を通すために
一時的な枝としてクレート内に置き、計測後に revert した（patch は #173 のコメントに残した）。
