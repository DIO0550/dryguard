### 1. NaN の閾値が、パニックの理由を取り違えるメッセージで落ちる

- 分類: `なし`
- 出どころ: レビュー
- 内容: 新しく足した `Threshold::from_literal`（`const fn`）は
  `assert!(value >= 0.0, "閾値は 0.0 以上")` → `assert!(value <= 1.0, ...)` の 2 段だった。
  NaN はどの比較でも false になるため、**NaN を渡すと「閾値は 0.0 以上」で落ちる**。
  doc には NaN でパニックすると書いてあるので嘘ではないが、出るメッセージは
  「範囲外の数値を書いた」と読める。NaN 専用の assert を先頭に足して直した（`4fdb761`）。
- 既存ルール: **なし。** 近いのは `rules/coding.md`「生成時に検証し、不正な値を存在させない」
  （その例の `Threshold::new` は同じ理由で `is_nan()` を先に見ている）と
  「エラー型は原因ごとにバリアントを分ける」（原因ごとに分けて `Display` で人が読む文にする）。
  ただし**どちらも値と `Result` の型の話で、パニックのメッセージが原因と対応しているかは
  書かれていない。** 既存の規約を守っていても今回の形は通り抜ける
- 次にどう防ぐか: 今回は記録のみ

  **注記（数えるための材料）**: `分類: なし` としては 5 件目。昇格の目安（10 件）には
  達していない。**ただしこの 1 件は「規約が無い」側で、「規約はあるがタグが無い」側ではない。**
  `rules/coding.md` は値の検証と `Result` の粒度を定めているが、**検証が落ちるときの
  メッセージ**については何も言っていない。

  昇格させるかの判断と置く層の選択は棚卸しの回の管轄（この回では行わない）。

## 手戻り

3 回。**どれも実装中に気付いたもので、捨てた設計は無い。**

1. **`Threshold::new` が `Option` を返すので `const` にできなかった。** 閾値をハードコードで
   持つには定数が要るが、`unwrap` は `Cargo.toml` の `[lints.clippy]` が落とす（それでよい）。
   `const fn` + `assert!` の `from_literal` を足して、範囲外はコンパイル時に落ちる形にした。
   **計画を書く前に気付けていた**ので、Issue のコミット計画には最初から入っている。

2. **`clippy::manual_range_contains` を踏んだ。** `value >= 0.0 && value <= 1.0` は
   `RangeInclusive::contains` を勧められるが、それは `const` で使えない。
   assert を 2 つに分けて回避した（`#[allow]` は足さない）。

3. **`Reason::lean()` を書いてから消した。** 実装した時点でどのテストも要求しておらず、
   `rules/tdd.md`「前提として守るもの」の Green（テストが要求しない機能を先回りで実装しない）に
   反する。必要になるのは `--explain` を作る回。**コミット前に自分で気付いて消した**ので、
   指摘としては数えていない。

## うまくいったこと

1. **閾値を決める前にフィクスチャの実測値を取った。** 当初は「ドメイン一致 = 依存先の重なりが
   高い **かつ** 距離が近い」で組もうとしていたが、`utils/formatDate.ts` <->
   `report/dateHelper.ts` が兄弟ディレクトリ（2 段）で、計画の出力イメージでは
   `EXTRACT-CANDIDATE` になる組だった。この条件では `REVIEW` に落ちる。
   **実測を先に取っていたので、計画を書く段階で気付いて条件を変えられた**
   （距離は「不一致」側の裏付けにだけ使う形）。`AGENTS.md`「実装を始める前に」の
   「計画の入力を鵜呑みにしない」が効いた形。

2. **疑わしい assert に変異を入れて確かめた。** `rules/testing.md`「迷ったら、その 1 件だけ
   実装を壊して走らせる」に従い 2 件試した。

   | 入れた変異 | 落ちたテスト |
   |---|---|
   | ドメイン不一致の条件からモジュール距離を外す | `..._in_the_same_directory_without_shared_dependencies_is_review` |
   | 既定の閾値を 0.85 → 0.5 に落とす | `..._below_the_threshold_is_review` ほか 1 件 |

   どちらも落ちたので、この 2 つの assert は判定の分かれ目を実際に捉えている。

3. **判定を「根拠が持つ傾き」から組み立てた。** ドメインの一致は `Lean` を材料にして決めており、
   同じ条件を判定用に書き直していない。`rules/architecture.md`「判定は 1 箇所にだけ置く」が
   守りたいもの（`--explain` の根拠と実際の判定が食い違わない）を、構造で担保できた。
