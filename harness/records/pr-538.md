## ゴールと結果

Issue のゴールは、ジェネリックな `typealias`（`typealias Pair<T> = (T, T)`）を通る型名について、
使用側の型引数を右辺へ当てはめて展開して比べること。達成した。`syntax::swift_callable` が
型パラメータを取る宣言を読み、右辺を宣言の順の番号で持つ。使用側の末尾の区切りの型引数を当てはめ、
型変数を展開後の出現順で振り直す。実サーバのテスト
`test_sourcekit_lsp_generic_typealias_applied_to_type_arguments_and_its_right_side_are_unifiable`
では、`coupled(value: Couple<Int>)` と `paired(value: (Int, Int))` が単一化可能、`mixed` とは単一化不能。
このテストは CI の `cargo test -- --ignored`（`.github/workflows/rust.yml`）で通った。

開かない側（偽陰性側）に倒したものは次のとおり。

- 型引数の数の不一致
- 前の区切りの型引数
- 境界を持つ宣言に使用側の型変数を当てる形
- 具体的な型の関連型（`C.Element`）
- `where` 節を持つ宣言

境界の要求が hover に出るかは未実測のまま残った
（[Issue の CI 結果のコメント](https://github.com/DIO0550/dryguard/issues/527#issuecomment-6852782592)）。

### 1. 境界を読み飛ばすと偽陽性になる場合を、計画が挙げていなかった

- 分類: `plan-case-omission`
- 出どころ: 自己修正（計画の検証）
- 内容: 計画は「境界は展開した型を変えないので読み飛ばす（Rust の generic alias も境界を制約に加えない）」としていた。
  検証で次の形を指摘された。Swift は境界を使用側の関数の要求として推論するのに、hover の綴りにはその要求が出ないはずなので、
  `Hashed<T: Hashable> = [T]` を通る `f<T>(x: Hashed<T>)` が `g<T>(x: [T])` と重なる。
  計画を直し、境界を持つ宣言に型変数を当てる形を開かない側へ倒した
  （[計画の検証のコメント](https://github.com/DIO0550/dryguard/issues/527#issuecomment-6852244089)）
- 既存ルール: references/plan-review.md「前提の裏取り」・rules/coding.md「列挙で判定を組むときは、漏れの倒れる向きを選ぶ」
- 次にどう防ぐか: 今回は記録のみ。Rust の扱いを根拠に Swift の振る舞いを決めるときは、言語ごとの意味の違いを入力の場合分けに挙げる

### 2. 展開に現れなかった型変数の扱いを、計画が挙げていなかった

- 分類: `plan-case-omission`
- 出どころ: 自己修正（計画の検証）
- 内容: 計画は「新しく出た型変数を展開後の出現順で番号付けし直す」とだけ書いていた。右辺に現れない型パラメータ
  （`Const<X> = Int` を通る `f<T, U>(x: Const<U>, y: T)`）で `U` が番号を取ったままだと、後ろの `T` の番号がずれて
  `f<T, U>(x: Int, y: T)` と重ならない。この場合分けが計画に無かった。番号を捨てる手順と単体テスト
  （`test_from_spelling_drops_type_variables_that_the_generic_alias_does_not_use`）を足した
  （[計画の検証のコメント](https://github.com/DIO0550/dryguard/issues/527#issuecomment-6852244089)）
