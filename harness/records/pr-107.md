## ゴールと結果

Issue #25 のゴールは「LSP サーバを子プロセスで起動し、JSON-RPC で会話できる土台を作る。
**TS と Rust でサーバを差し替えられる形**にしておく」。完了条件は
「typescript-language-server を起動し、`initialize` の応答（capabilities）を受け取れる」。**達成した。**

| やること | 結果 |
|---|---|
| `lsp-types` を入れる | 0.97.0 / `serde_json` 1.0.151 を `harness/deps/resolve.sh` 経由で追加 |
| JSON-RPC クライアントを自作する | `lsp::framing`（区切り）/ `lsp::message`（payload）/ `lsp::connection`（対応付け） |
| 子プロセスの起動・配線・終了 | `ServerCommand` / `Client::start` / `Drop` での kill |
| ライフサイクル | `handshake`（`initialize` → 応答 → `initialized`）/ `shutdown`（`shutdown` → 応答 → `exit`） |

完了条件は `#[ignore]` の実サーバテストで確認し、**CI に無条件で走らせるステップを足した**
（`cargo test -- --ignored`）。サーバの差し替えは `ServerCommand` が持つ形にした。

**ずれ: この PR の中身が 2 つになった。** レビューの過程で「CI が LSP サーバをどう入れるか」が
独立した設計判断として立ち上がり、#109 として分離登録したうえで**同じ PR に入れた**（ブランチを
分ける許可が無かったため）。結果として #25 の本体（`src/lsp` 4 ファイル）と #109 の CI 導入経路
（`package.json` / `pnpm-lock.yaml` / `resolve-node.sh` / ワークフロー）が 1 本になった。

**持ち越し: 応答待ち・終了待ちの期限と、起動時 stderr の保持。** 3 件とも「待ち続けている最中に
外から時間切れを判定する仕組み」という 1 つの決めごとに帰着するため #108 へ分離。
制限（サーバが黙り込むと CLI が止まる）は `docs/dryguard-plan.md` のリスク表に残した。

## 手戻り

- **レビューが 7 巡し、うち 2 巡は自分が入れた直後のコードへの指摘**（指摘 13 は 1 つ前のコミット、
  指摘 16 は 1 つ前の修正）。**4 巡目の 2 件がどちらも既出の論点の作り直し**だったため、そこで
  押し続けるのをやめて判断を仰いだ（結果は「持ち越し」で #108 へ）

- **pnpm の導入方法を 4 回変えた**: npm → corepack + `pnpm add -g` → corepack + lock →
  curl + SHA-256 + lock → `pnpm/action-setup`（commit 固定）+ lock。うち後半 2 回は
  レビューと指示による方針変更で、**最後の 1 回はマージ直前の指示**（公式以外のアクションを
  commit 固定で使ってよくなった）

## 規約への反映

**`count.sh` が数える `対策済` の行は書かない。** ルーティンの指示により、この回は記録の追記のみで、
集計と規約・フックへの介入は棚卸しの回の管轄。

**ただし「規約を一切触っていない」わけではない。** この PR は `AGENTS.md` に
「JavaScript 側のパッケージは pnpm で入れる」の節を足している（指摘 17 / 19 を受けて、
npm 禁止・cooldown 5 日・lock を commit する・`resolve-node.sh` を通す・アクションの固定条件）。
`harness/deps/README.md` にも JavaScript 側の節を足した。

**それでも `対策済` の行を書かないのは、これが分類に対する介入ではないため。** 足したのは
**依存の入れ方という領域の規約**で、`plan`（計画の誤り・不足）という失敗の形に効くものではない。
ここで `対策済: plan 層=rules` と書くと `count.sh` の再発数が 14 → 0 に戻り、
**「plan の再発に手を打った」という誤った信号**になる。`plan` に効く介入は打っていない。

**注記（数えるための材料）**: この回の `分類: なし` は 10 件
（指摘 1 / 3 / 6 / 9 / 10 / 11 / 12 / 14 / 15 / 16）。
**うち 6 件は 3 つの塊に分かれ、4 件はどこにも入らない。**
**塊は「対策が同じもの」で切ってある**（同じ対策で消えないものを 1 つに数えると、
語彙を割るときに効かない介入を選ぶ）。

| 塊 | 該当する指摘 | 形 | 対策 |
|---|---|---|---|
| 外部プロセスの入力に上限が無い | 3 / 6 | 長さを検査せずに確保・読み込みする | 上限を設ける |
| 待ちに期限が無い | 9 / 11 | 相手が黙ると自分が止まる（#108 へ分離） | 期限を設ける |
| 検査がフェイルオープン | 15 / 16 | 「書いてあるか」だけ見る / 無効な値を通す | 効いている値を見る |

**塊に入らない 4 件:**

- **指摘 1**（サーバの要求に答えず双方が待ち合う）: 待ちに関わるが、「待ちに期限が無い」が
  *相手が黙ると自分が止まる*のに対し、こちらは*自分が答えないので相手が止まる*。**向きが逆**で、
  対策も違う（期限を設ける / 応答を返す）
- **指摘 12**（起動時の stderr を捨てており診断が消える）: **この回で唯一、欠陥が残っている件。**
  中間案（`ServerClosedDuringHandshake`）は入れたが、診断そのものは今も取れない。
  対策は #108 の「吸い続ける側を置く」で、他の塊のどれとも違う
- **指摘 10**（`Content-Length` の重複を後勝ちで読む）: **上限の話ではない。** 長さは分かっていて、
  **どちらが本当かが決まらない**のが問題。対策は上限ではなく「曖昧なフレームを弾く」なので、
  3 / 6 と同じ塊に入れると、上限を入れても消えない欠陥を上限の再発として数えることになる
- **指摘 14**（`initialize` の error の `data` を捨てている）: **却下した指摘**。塊にすると
  「直さなかったもの」が「繰り返している問題」に混ざる

3 つ目の塊は**この PR の中で 2 巡続いた**うえ、指摘 21（自分が検査を通さずに lock を作った）とも
同じ根を持つ。`TEMPLATE.md` は「`分類: なし` が 10 件溜まったら語彙へ昇格させる」としており、
この回で通算 8 → 18 になる。**どう割るか（塊ごとに語彙を立てるか、入らない 4 件をどう扱うか）は
棚卸しの回で扱う。**

`plan` はこの回だけで 5 件（17〜21）で、いずれも**「手元で確かめた」の中身がランナー / 規約の
要求と揃っていなかった**形。**この 5 件で `plan` の再発は 14 → 19 になり、分類の中で最多**
（`count.sh` の「再発」は最後の介入以降の数で、`plan` は未介入なので通算と一致する）。
