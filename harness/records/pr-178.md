## ゴールと結果

Issue #86 のゴールは「短い関数で構造類似度が過大に出る」を直すこと。**直す実装は入れていない。
測り直したら、既に解けていた。**

| ゴール（Issue #86 の完了条件） | 結果 |
|---|---|
| `allocate` ↔ `renderInvoiceEmail` が候補に上がらない | **達成済みだった。** 構造類似度 0.44（既定の閾値 0.50）で候補外 |
| 妥当だった例（`overdueInvoices` ↔ `itemsInWarehouse`）が候補に残る | **達成済みだった。** 0.79 で候補・`DO-NOT-EXTRACT` |
| 判定ルールを触るので、先にテストを書いて Red にする | **触るルールが無かったので回していない**（下記） |

**Issue が挙げた「検討の方向」の 3 つ目（`tree-sitter` の AST 正規化を入れてから測り直す。
これで解ける可能性があるので、先に確かめる）に従って先に確かめた結果**、構造類似度が
正規化トークンの集合 Jaccard から正規化トークン列の 3-gram（出現回数つき）へ変わった時点で
この形は消えていた。`tests/corpus/src` の全 1081 ペアを既定の閾値 0.50 で測り直すと、
**短い側が 3 行のペアの候補率 1.8%（340 ペア中 6）に対し、10 行のペアは 56.9%（51 ペア中 29）**で、
短さが有利に働く向きが逆転している。

**完了条件は既に層 1 に載っていた。** `GRAM_LENGTH` を `3` → `1`（並びを見ない = 集合で
数えるのと同じ）に壊すと `allocate` ↔ `renderInvoiceEmail` は 0.44 → 0.64 に戻り、
`tests/compare.rs::test_compare_of_two_short_functions_without_a_shared_shape_is_review` と
`tests/scan.rs::test_scan_of_the_corpus_leaves_out_a_pair_that_is_not_structurally_similar`
（対照つき）が落ちる。確かめてから、同じ振る舞いを見るテストは足さないと決めた。

**したがってこの PR は doc コメントと Markdown だけ**で、却下した案の理由（`GRAM_LENGTH` の
Why not）と、測り方が変わって古くなった記述の修正に絞った。

**残った形は #182 として分離した。** 本体が 1 文だけの関数どうしは、シグネチャと `return` の
骨格が gram の多くを占めるため、いまも 0.50〜0.53 で候補に乗る（`shouldRetry` ↔ `roundToCents`
0.53 など 3 組）。判定自体は `REVIEW` / `DO-NOT-EXTRACT` に落ちているので、直す動機は
候補列挙のコスト（Stage 2 の LSP 問い合わせ）だけ。`AGENTS.md`「設計判断の確認」に当たるため
選択肢と根拠を Issue に出して判断を仰ぎ、許可を得てから登録した。

### 1. 候補率に、使った閾値を書いていなかった

- 分類: `unverified-claim`
- 出どころ: レビュー（Codex、`277a3e4` の巡、P2）
- 内容: `tests/corpus/README.md` に「短い側が 3 行のペアの候補率は 1.8%、10 行のペアは 56.9%」と
  書いたが、候補かどうかは構造類似度の閾値で決まるのに閾値を書いていなかった。**3-gram という
  測り方だけからは再現できない数値**で、閾値を測り直した後は、この数値がまだ成り立つのかを
  読む側が判断できない。`bdb460e` で「既定の閾値 0.50 で」を明記し、閾値を測り直したら
  数値も出し直すことになる旨を足した
- 既存ルール: `AGENTS.md`「記録・PR 本文に数値や主張を書く前に」（**ただし射程の外**。
  あの節が列挙しているのは記録・PR 本文・Issue コメント・コミットメッセージ・レビュー返信・通知で、
  **リポジトリのドキュメント（README）は入っていない**。`comment-mismatch` の射程は
  `rules/coding.md` のコード内 doc コメントなので、そちらでもない）
- 次にどう防ぐか: 今回は記録のみ（射程の話は「規約への反映」に書く）

### 4. 「最小トークン数の下限」を却下する理由を、行数で書いていた

- 分類: `unverified-claim`
- 出どころ: レビュー（Codex、`e4ceb1c` の巡、P2）
- 内容: 却下した案は最小**トークン数**の下限なのに、`GRAM_LENGTH` の Why not に
  「同じ長さの真陽性（`taxFor` ↔ `netOf`）を先に削る」と**行数**で書いていた。`tokens_of` で

  行数でも取っていたので、そちらの数字で理由まで書いてしまった形。`68166b5` で
  「下限を偽陽性（`allocate` 49 トークン）に届く高さにすると真陽性（`taxFor` 37 / `netOf` 43）が
  先に消える」に書き換えた（却下の結論は変わらない）。**同じ誤った理由を Issue #86 の
  コメントにも書いていた**ので、訂正コメントを出して選択肢の表も直した
- 既存ルール: `AGENTS.md`「記録・PR 本文に数値や主張を書く前に」（Issue コメントは射程内。
  rustdoc 側は指摘 1 / 2 と同じ射程の外）
