### 1. doc が書いている「シンボリックリンクを辿らない」を、どのテストも見ていなかった

- 分類: `test-coverage-gap`
- 出どころ: レビュー（Copilot）
- 内容: 「`is_symlink()` を見ていないので symlink ディレクトリを辿りうる」という指摘。
  **指摘そのものは現行実装には当たらない。** `fs::DirEntry::file_type()` はリンク自身の型を
  返す（`symlink_metadata` 相当）ので、symlink のディレクトリは `is_dir()` が false になり
  走査対象に積まれない。実際に `linked-billing -> billing` を作って確認した。

  ただし**この性質を守っているのは `entry.file_type()` を使っていることだけ**で、doc に
  書いてある性質をどのテストも押さえていなかった。`path.is_dir()`（`chunk-unit-probe` が
  使っている形）へ書き換えると本当に辿る。フィクスチャにシンボリックリンクを置き、
  リンク経由のパスが走査に出ないことをテストで固定した。`path.is_dir()` に壊すと 5 件落ちる。
- 既存ルール: `rules/testing.md`「振る舞いをテストする」。**doc に書いた性質は
  「外から観測できる振る舞い」なので射程内**だが、規約は「テストを書く対象」を
  差分の中心として語っており、**「doc で約束したこと」を対象に挙げてはいない**。
- 次にどう防ぐか: 今回は記録のみ

### 2. 型を 1 つ返す関数を、自由関数として置いた

- 分類: `module-api`
- 出どころ: レビュー（作者）
- 内容: 「FileChunks の関数でいいのでは？」。`chunks_of(path, tree)` を自由関数として
  置いていたのを `FileChunks::from_tree(tree, path)` に移した。

  自由関数にした根拠は `rules/naming.md`「複数をまとめて返すものは `<返すもの>_of`」
  だったが、**あれは複数をまとめて返す関数の形**で、`FileChunks` という型を 1 つ返す
  ここには当てはまっていなかった。このリポジトリには既に `ImportSet::from_tree` /
  `TokenSequence::from_node` / `SyntaxTree::from_typescript` という
  「その型を作る関連関数」の形があり、**同じモジュールの中で語彙が割れていた**。
- 既存ルール: `rules/naming.md`「`create` / `new` / `from_*` の使い分け」に
  「`from_*`: 別の表現から作り直すとき」がある。`<返すもの>_of` の項と**どちらが効くかが
  書かれていない**ため、`_of` を先に読んで当てはめた。
- 次にどう防ぐか: 今回は記録のみ
