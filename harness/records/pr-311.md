## ゴールと結果

直接囲む trait impl の `Self::Item` / `<Self as Trait>::Item` を関連型の右辺へ展開し、
明示した型と比較できるようにした。impl 型変数と GAT の型引数を代入し、右辺の型名は
宣言側の位置から解決する。trait メンバーの所有 trait と impl の実装 trait の宣言位置を
照合し、別 trait の同名メンバーを流用しない。

rust-analyzer の使用位置への hover / definition は trait の関連型宣言を返し、
typeDefinition / implementation から選択した impl は得られなかった。
[実測と分割・計画](https://github.com/DIO0550/dryguard/issues/303#issuecomment-5995519876)
に基づき、直接囲む impl の定義を読む範囲へ絞った。別 impl の選択、入れ子の投影、
関連型 RHS の Self は #310 に分離し、未対応の選択と展開できない定義は別の理由で出す。

#303 は PR のマージで閉じた。マージ後の記録作成時に再レビューのテスト一覧の漏れを
コードで確認し、独立した補完として #313 に残した。関連型解決の実装を変更する課題ではない。

## 手戻り

- 使用位置の hover だけによる展開、typeDefinition / implementation の先頭を具体的な impl と見なす案、関連型の末尾名だけで同一視する案は、実測と誤一致の懸念から却下した。
- `SourceDocument::source()` を crate 内へ公開し、LSP サーバへ送ったソースから直接の impl 文脈を読む判断を加えた。使用側でファイルを読み直して問い合わせ対象とずらさず、ステージの再配置は行わなかった。
- 完全修飾形の空白・コメントを AST の字句から正規化した。別の trait パス綴りや既定の型引数を含む一般的な impl 選択は #310 に残した。
- `test_rust_impl_signatures_preserve_target_receiver_bounds_and_binding_scopes` の projected の期待値を先に変え、既存の `SiteDependentSpelling` で失敗することを確認した。この意図した Red 自体は欠陥として数えない。
- [着手時の記録](https://github.com/DIO0550/dryguard/issues/303#issuecomment-5995466323)と[レビュー修正時の記録](https://github.com/DIO0550/dryguard/issues/303#issuecomment-6016601688)によると実行環境は Codex。`echo hook-canary` は通ったが、起動時の設定読み込みを確認できず層3の発火は未判定。セッション URL は得られず推測していない。CI の hooks テスト成功からセッション内の発火は推定しない。
- [公開時の記録](https://github.com/DIO0550/dryguard/issues/303#issuecomment-5995953529)によると shell の push は HTTPS 認証情報がなく失敗した。GitHub プラグインで、ローカル検証済み tree と一致する tree を登録して公開した。レビュー修正時も同じ経路を使い、検査と本文の差分規模確認を公開前に実行した。

## うまくいったこと

- LSP の応答を実測してから直接囲む trait impl に対応範囲を絞り、選べない impl を綴りの一致だけで比較しなかった。
- 宣言側と使用側の同名型・型変数、GAT の個数・種類、異なる trait 引数、条件付き定義、UTF-16 の問い合わせ位置を対照テストで確認した。
- 選択できない関連型と、選んでも展開できない関連型の理由を区別して text / JSON に出した。
- 再レビューの総評だけで完了とせず、具体的な欠落の指摘をコードと照合して後続 Issue へ残した。
