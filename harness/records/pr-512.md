## ゴールと結果

Issue #500 のゴールは、`extension Array where Element == Int { … }` や `extension Array<Int> { … }` のメンバーで型シグネチャを測れるようにすること。それまでは `SwiftEnclosingType::Constrained` にして型シグネチャを読まなかった（`UnreadableSignature`）。

- 達成した:
  - `SwiftEnclosingType` を、囲む宣言の型と `where` 節のソースの綴りを持つ struct にした。`SwiftCallable::from_spelling` がそれを `extension <綴り> {}` として読み、レシーバの型（型引数を含む）と `where` の述語（`receiver_constraints`）を足す（`src/syntax/swift_callable.rs`）
  - `where` の左辺はレシーバからの相対の綴りで持ち（辿らない）、右辺と型引数は型名として辿る（`enclosing_type_references_of` が位置付きで集める）
  - 実サーバのテスト 3 件を足した（`tests/swift_lsp.rs`）。CI の Rust（run 884 / 888）の `cargo test -- --ignored` で通った
- Issue とのずれ:
  - 省略形で書いた拡張（`extension [Int]` / `extension Int?`）は、それまで囲む型が `None` になっていた。自由関数と同じレシーバ無しで比べる偽陽性で、計画の段で見つけてこの PR で塞いだ（Issue #500 の 2 つ目のコメント）
  - 型の宣言の `where`（`struct Box<T> where T: Equatable`）と `extension Outer<Int>.Inner` も読むようになった（main では `Constrained`）
  - `extension Array<Int>` と `extension Array where Element == Int` は重ねていない（偽陰性側）。型変数が何番目の型引数かは、宣言を読まないと言えないため。計画のコメントで「完了後に別 Issue にする」と書いた

実測した前提（Issue #500 の 2 つ目のコメント）: sourcekit-lsp 6.4.2 を swift.org から取り、実装したセッションのローカルで走らせた。

- メンバーの hover は extension の `where` を綴らない
- `where` の左辺 `Element` の definition は、宣言ではない位置（`Shop.swiftinterface` の 1 行 0 列）を返す
