## ゴールと結果

Issue #18 の未決事項「チャンクの単位（関数単位で足りるか、ブロック単位まで落とすか）」を
**関数・メソッド単位で確定**した。

**判断材料が揃っていなかったところから始めた。** #18 の判断軸は「Phase 0 の検証で偽陰性が
多いか」だが、`harness/phase0/verify.sh` は `compare` を呼ぶため出てくるペアが常に関数単位で、
**関数の一部だけの重複を取りこぼしているかは定義上その数に出ない**。#17 の検証も
`DO-NOT-EXTRACT`（偽陽性）側しか見ていなかった。そこで計測（`harness/phase0/chunk-unit-probe/`）を
足してから数えた。

**結果: `tests/corpus`（47 関数 / 1081 ペア）で、ブロック単位にして初めて閾値 0.85 を
超える関数ペアは 8 件（0.7%）。** 目視の内訳はガード節 2 / 加算ループ 2 / フィルタループ 3 /
ループ骨格 1 で、**すべて言語のイディオム**。関数の一部が業務上の重複だったケースは 0 件。
一方でコストは比較の単位 47 → 87、ペア 1081 → 3741（3.5 倍）、ブロックのトークン数は
中央値 17（関数は 39）で**全ブロックが #86 の領域に入る**。

**ずれ 1**: このコーパスは自前なので、8 件が実コードでの偽陰性の頻度を表さない。
コーパスの関数は中央値 6 行と短く、**長い関数ほど起きやすい部分重複は実コードのほうが多いはず**
なので過小に出ている可能性が高い。再検討の条件を計画に書き、対象の入手を #88 に紐づけた。

**ずれ 2**: セッション中に依存の cooldown（#91）が話題になり、**同じ PR に載せた**。
差分は 2 倍近くになったが、#90 で足した `chunk-unit-probe` の lock が現に `cc 1.4.4`
（当時公開 1 日）を掴んでおり、**修正と再発防止を別 PR にすると片方だけ入った状態が生まれる**
ため分けなかった（判断は #91 に記録）。

### 1. 防御の層を間違えた提案をした（CI で lock を検査する案）

- 分類: `plan`
- 出どころ: レビュー（セッション中のオーナー発言）
- 内容: 依存の cooldown をどこに置くかを聞かれ、**CI で `Cargo.lock` の `pubtime` を
  検査する案を「推奨」として出した**。「CIじゃなくね？最初にブロックしてないと意味ないじゃん」
  と指摘され、初めて誤りに気付いた。

  悪意あるバージョンは build script と proc macro が `cargo build` の時点でローカル実行される。
  **CI が赤くなる頃には自分のマシンで実行済み**なので、CI は事後検知にしかならない。
  `AGENTS.md`「強制力の序列」を機械的に当てはめ（層 1 = CI が最上位）、
  **序列が「検査が確実に走るか」で並んでいて、この件で要るのは「コードが実行される前か」
  である**ことを見落とした。
- 既存ルール: `AGENTS.md`「強制力の序列」。**規約の抜けではなく、適用の誤り。**
  ただし序列が逆転する場面があること自体はどこにも書かれていなかったので、
  今回の実装（#91）の一部として `AGENTS.md`「依存の更新は cooldown を通す」に明記した。
- 次にどう防ぐか: 今回は記録のみ（規約への反映は下記のとおり実装に含めた）
