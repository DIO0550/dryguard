## ゴールと結果

Issue #170 のゴールは「アクセサ（getter / setter）の型シグネチャが、取れないだけでなく
**関数型のときは誤って取れる**（偽陽性）」を止めること。Issue は案 A / B / C を挙げて
判断を仰ぐ形で終わっていたので、着手時にセッション URL を残したうえで実測を取り直し、
判断を仰いだ。**案 C（理由を足して、`SplitSignature` で割る前に落とす）**で進めることになり、
偽陽性は止まった。

**ずれ: 案 A-3（`TypeSignature` が持つのを `Callable` ではなくチャンクの型の enum にする）は
この回に入れていない。** Issue #120 が挙げた「取れない形を減らす」には届いておらず、
アクセサのシグナルは引き続き付かない。#176 に切って引き継いだ（下の「手戻り」ではなく、
着手前に決めたスコープ）。

### 2. アクセサの理由が、相手側の理由に隠れていた

- 分類: `missing-signal`
- 出どころ: レビュー（Codex P2）
- 内容: `type_signature_match_of` のアクセサの枝を最後に置いたため、片側が
  `AccessorSignature`、もう片側が `UnopenedTypeName` のときに後者が出ていた。利用者は
  型エイリアスを開けるように直して走らせ直すが、アクセサ側は扱えないままなので
  **直しても同じペアは測れない**。枝を、両側が正規化できた枝の直後へ移した。
  1 件だけ動かすと `NoTypeThere` / `HoverNotProvided` と組んだときに同じことが起きるので、
  並びに「**環境を直しても変わらない理由を先に出す**」という軸を入れ、関数の doc と
  回帰テストで固定した
- 既存ルール: rules/architecture.md「取れなかったシグナルを既定値で埋めない」の
  「理由は落とさない」（**利用者が次に何をするか**を理由が持つ）。Codex も L87-89 を引いている
- 次にどう防ぐか: 今回は記録のみ。規約は「理由を落とすな」までは書いているが、
  **理由が複数あるときにどれを出すか**は書いていない。今回は関数の doc に軸を置いた。
  同じ形（理由の選び方）が再発したら `rules/architecture.md` へ上げる

### 3. Discord へ送れていないのに「送った」と書いた

- 出どころ: 自己修正

  数えるのは棚卸しの回に任せる

## うまくいったこと

- **assert を壊して確かめた。** `is_accessor_spelling` を常に `false` / 常に `true` に
  して走らせ、3 件 / 126 件が落ちることを見た（`rules/testing.md`「迷ったら、その 1 件だけ
  実装を壊して走らせる」）。理由の並びについても、枝を元の位置へ戻して落ちることを見た
- **直す前に、純粋な側で偽陽性を再現した。** 実サーバが無い環境でも
  `normalized_outcome_of` へ綴りを直接渡せるので、E2E が使う綴りそのもの
  （`(setter) Holder.handler: (message: string) => void` と
  `(method) Notifier.notify(value: string): void`）で `unifiable = true` を確かめてから
  テストを足せた。`rules/tdd.md`「`lsp` は『応答を受け取ってから先』を切り出す」が
  効いている
- **CI の失敗を、CI を回さずに再現した。** 指摘 1 の `NotACandidate` は Stage 1 の話なので
  LSP 無しで測れた。閾値との余白（0.556 では 1 割しか無い）まで見て 0.649 に直せた
- **Issue が判断を仰ぐ形で終わっていたので、実装に入らず止めた。** 止める前に実測を
  取り直し、Issue が書いていなかった 4 点（偽陽性が `is_unifiable_with` まで届く /
  Stage 1 → Stage 2 の経路がつながる / `(property)` はずれない / A-1 の前提）を足せたので、
  判断の材料が増えた状態で再開できた
