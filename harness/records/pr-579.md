# PR #579 Swift XCTestCase の extension にあるテストメソッドを走査から除外する

- マージ日: 2026-11-28（`merged_at: 2026-11-28T08:57:54Z`）
- 関連 Issue: [#521](https://github.com/DIO0550/dryguard/issues/521)
- 差分規模: 20 ファイル / +817 -67

## ゴールと結果

Swift で、`XCTestCase` を直接継承するクラスの `extension` に直接書いた引数なしの `func test…` を
`scan` / `check --diff` の既定の比較対象から外す。別ファイルの照合は、走査対象の最寄りの SwiftPM
マニフェスト（バージョン別も含む）で、両者が同じ単一のテストターゲットに属すると確認できる場合に絞った。
所属を確認できない別ファイルの拡張は残る。`--include-tests`、`compare`、参照元ドメインの扱いは変えていない。
`--staged` は型宣言もマニフェストも index の版を使う。

差分規模は [マージコミット](https://github.com/DIO0550/dryguard/commit/ddbc379a254e3a44181fecd510bdef4f6bddbd14) と第 1 親の `git diff --shortstat` で確認した。

## 指摘

### 1. 別のターゲットで拡張した同名の型まで XCTest 扱いになった

- 分類: `input-form-omission`
- 出どころ: [Devin のレビュー（P2）](https://github.com/DIO0550/dryguard/pull/579#discussion_r4724776301)
- 内容: `e8e1a89` はトップレベルの型名を走査全体で照合していた。別ターゲットにだけ `class Date: XCTestCase` があると、
  本番側が Foundation の `Date` に書いたメソッドまで除外した。`9c0c670` で同一テストターゲットと確認できるものに絞り、
  本番ターゲットと別テストターゲットの Foundation 拡張は残し、本来の XCTest 拡張は外す回帰テストを追加した。
- 既存ルール: `.claude/skills/implementation-flow/references/implementation-review.md`「シグナルと判定」の入力の形の項
- 次にどう防ぐか: ファイル間で型名を照合するときは、同一・別ターゲット、所属不明の組を対照にする。今回は記録のみ。

### 2. Swift の走査で全ファイルの構文木が一度に生存した

- 分類: `なし`
- 出どころ: [Devin のレビュー（P3）](https://github.com/DIO0550/dryguard/pull/579#discussion_r4724776303)
- 内容: `e8e1a89` はテスト除外時に Swift ファイルをすべて `OwnedSyntaxTree` として保持していた。
  `9c0c670` では各ファイルの処理中に木を解放し、照合待ちのファイルだけ初回のソースを保持して再解析する。
  ファイルを読み直さず、宣言とチャンクの版を揃えた。
- 既存ルール: なし（ファイル横断の前処理で保持するデータ量の観点）
- 次にどう防ぐか: 一覧を作る前処理を足すときは、ファイル数に比例して何が生存するかを確認し、大きな同一入力でピーク RSS を測る。今回は記録のみ。

### 3. 同名宣言の競合に入る型の形が計画に明記されていなかった

- 分類: `plan-case-omission`
- 出どころ: 自己修正（[計画の検証](https://github.com/DIO0550/dryguard/issues/521#issuecomment-7231233424)）
- 内容: 当初の計画は同名宣言が複数なら残すとしていたが、クラス以外の同名型や `typealias` も競合になることを列挙していなかった。
  文法から型宣言の形を確認し、struct・enum・actor・protocol・typealias も競合として扱い、照合順を入れ替える回帰も足した。
- 既存ルール: `implementation-flow`「3. 計画」の入力の形を出どころと一緒に挙げる項
- 次にどう防ぐか: 型の候補一覧は、一致する宣言だけでなく一致を妨げる宣言も文法から引く。今回は記録のみ。

### 4. ファイル限定のクラスを別ファイルの照合根拠にできていた

- 分類: `input-form-omission`
- 出どころ: 自己修正（[実装の検証](https://github.com/DIO0550/dryguard/issues/521#issuecomment-7231353897)）
- 内容: 初回の実装検証で、`private` / `fileprivate` の型は別ファイルから見えないという対照が抜けていた。
  初回 PR の公開前に同じファイル内に限るよう直した。制限を無効にすると回帰テストが失敗することも確認した。
- 既存ルール: `.claude/skills/implementation-flow/references/implementation-review.md`「シグナルと判定」の入力の形の項
- 次にどう防ぐか: スコープを跨ぐ照合で使う可視性を同じファイル・別ファイルの両方で試す。今回は記録のみ。

## うまくいったこと

- Swift Argument Parser 1.6.1（`309a47b`）を sourcekit-lsp なしで `dryguard scan --lang swift --format json <root>` し、
  記録時にも走査 JSON を集計し直した。修正前 main（`cb8abec`）から除外テスト関数は 66 → 523、
  候補ペア全体は 10,677 → 706、両方が `Tests/` 配下のペアは 9,993 → 22。
  同一ターゲットに絞った後も、初回 PR より除外効果が落ちていないことを同じ入力で確認できた。
- 構文木の保持を見直した効果は、Swift の合成入力（192 ファイル、各 1,500 行のプロパティ宣言）で測った。
  記録時に Linux の debug ビルド、`RAYON_NUM_THREADS=4` で `scan --lang swift --format json` を各 3 回再実行し、
  `wait4` のピーク RSS の中央値は `e8e1a89` の 425,104 KiB から修正後の 28,700 KiB になった。
  実コーパス全般のメモリ改善率ではなく、チャンクを持たない入力で構文木の保持の差を測った結果。
- 初回と修正後のコミットで Rust と差分規模のワークフローが成功した。修正コミットを公開した直後の

  本文更新後の[実行](https://github.com/DIO0550/dryguard/actions/runs/46127277870)が成功した。
  修正後の [Rust CI](https://github.com/DIO0550/dryguard/actions/runs/46127273510) では最低対応 Rust、fmt / Clippy / test、
  実 LSP テスト、Claude Code hooks のテストも成功した。
