## ゴールと結果

Issue のゴールは「2 つのチャンクの構造類似度を 0-1 の数値で出す」。
完了条件（出力イメージの `構造類似度: 0.91` に相当する値が出る）は満たした。
実測は名前と定数だけが違うフィクスチャ同士で **0.94**、ループと配列を持つ関数との組で **0.59**。

**ずれ**: スコープに無かった変更が 3 つ入った。いずれもレビューでの判断による。

- `rules/naming.md` の改訂（`collect_*` を外して `<返すもの>_of` に差し替え）
- `pipeline::collect_chunks` / `ChunkCollectionError` の改名（Stage 1 の外）
- `syntax::source_character` の新設（文字種の判定を `token` から移動）

1 つ目は規約を直さないと実装と食い違うため同梱した。2 つ目は 1 つ目に従属する。
3 つ目は「独立してマージできるか」で見ると分けられたが、**指摘の対象そのもの**だったので同梱した。

## 指摘

### 1. `end_of_number` が数値へのプロパティアクセスを飲み込む

- 分類: `なし`
- 出どころ: レビュー（Copilot）
- 内容: `.` と ASCII 英数字を無条件に数値の一部として読んでいたため、`1.0.toFixed(2)` が
  `Number` 1 個に潰れ、`Symbol('.')` と `Identifier` が消えていた。**構造類似度は
  「構造が同じか」を見るシグナルなので、構造が消えた側が実際より似て見える**。
  再現テストを先に書いて Red にしてから直した
- 既存ルール: なし
- 次にどう防ぐか: 今回は記録のみ

  **注記（数えるための材料）**: これは pr-67 の指摘 1（行継続した文字列の中の閉じブレースを
  本体の終わりと誤検出）と**同じ形**。どちらも素朴な走査が黙って間違った結果を返し、
  `rules/architecture.md`「取れなかったシグナルを既定値で埋めない」の裏側にあたる
  「間違った値で成功させない」が明文化されていない。**分類 `なし` としては 2 回目**。
  規約へ昇格させるかの判断は棚卸しの回に行う

### 2. `collect` という単語を名前に使わない

- 分類: `naming-vocabulary`
- 出どころ: レビュー
- 内容: `Token::collect_from` に対して「Collect という単語を使わないようにしたい」。
  範囲を確認したところ「リポジトリ全体で使わない」だった。
  `Token::collect_from` → `tokens_of`、`pipeline::collect_chunks` → `chunk_pair_of`、
  `ChunkCollectionError` → `ChunkPairError` に改名した
- 既存ルール: rules/naming.md「`create` / `new` / `from_*` の使い分け」が
  **「収集は `collect_*`」と逆を定めていた**。指摘どおりに直すと規約違反になる状態
- 次にどう防ぐか: ルール修正（実施済み）。「収集は `collect_*`」を
  「複数をまとめて返すものは `<返すもの>_of`」に差し替え、「`collect` を名前に使わない」の項を足した

  **分類の選び方**: `naming-mismatch` とも読める（`collect_from` は実際には集めておらず、
  ソースを別の表現へ直しているだけだった）。ただし**それは指摘を受けてこちらが見つけた分析**で、
  指摘そのものは「この語を語彙から外す」だったので `naming-vocabulary` を選んだ。
  `naming-mismatch` として数えるなら pr-67 に続く 2 回目になる

### 3. 文字種の判定を `token` の外へ置きたい

- 分類: `なし`
- 出どころ: レビュー
- 内容: 「ここら辺 char 自体に impl できないんだっけ？それか、token 以外のところに配したい」。
  `impl char` は書けない（`error[E0390]: cannot define inherent impl for primitive types` を
  実際にコンパイルして確認）。置き場所の案 3 つを出して B（自由関数のまま新モジュールへ）で決まり、
  `syntax::source_character` を新設した
- 既存ルール: なし。`rules/architecture.md` はモジュール**間**の責務と依存方向を定めているが、
  1 つのモジュール内のヘルパーをどこまで外へ出すかは書かれていない
- 次にどう防ぐか: 今回は記録のみ

### 4. 同じ文字種の判定が `chunk.rs` にもある

- 分類: `duplication-logic`

- 既存ルール: なし（`duplication-logic` は分類の語彙にあるが、対応する `rules/` の項は無い）
- 次にどう防ぐか: 今回は記録のみ。**#70 に分割した**。判断軸は `AGENTS.md`

## 手戻り

3 回。**実装を捨てた手戻りは無く、3 つとも自分の書き損じか回答の変更による。**

1. **回答が A → B に変わった。** 「`collect` の範囲」を確認して「A（この 1 箇所だけ）」の
   回答をもらい、「追加変更なし」と返信した直後に「やっぱり B で」と変更された。
   A の時点で追加のコードを書いていなかったので捨てたものは無いが、
   PR のスレッドに行き違いの返信が 1 つ残り、訂正のコメントが要った
2. **コミット本文の見出しを打ち間違えた**（`影響とトレードOFF`）。push 前に気づいて amend した。
   見出しは `git log --grep` の検索性が表記の統一に依存するため、揺れると検索から漏れる
3. **実在しないスレッド ID をコミット本文に書いた。** 参考リンクの番号を確かめずに書き、
   push 前に実際の ID を取得して amend した。**推測で書いた値がそのまま残るところだった**

## うまくいったこと

- **素朴な集合 Jaccard で足りるかを、実装前に手で見積もった。** 「識別子を 1 つに潰すと
  集合が小さくなりすぎて何でも似て見えるのでは」を先に確かめ、0.94 / 0.61 / 0.47 に
  分かれる見込みを得てから素朴な実装に決めた。実測は 0.94 / 0.59 で見積もりとほぼ一致し、
  用意していた代替案（多重集合の重み付き Jaccard）は使わずに済んだ
- **assert が落ちうるかを、実際に壊して確かめた。** Jaccard が常に 1.0 を返すよう変異させ、
  「高い類似度が出る」だけを見るテストは**壊しても通る**こと、対照を置いたテストだけが
  落ちることを確認した（`rules/testing.md`「迷ったら、その 1 件だけ実装を壊して走らせる」）。
  対照用フィクスチャ `tests/fixtures/report/summary.ts` はこの確認の結果として足したもの
- **設計判断で 2 件とも止めて、選択肢と根拠を出した。** どちらも推奨した案が採用された。
  特に指摘 3 は `impl char` が書けるかどうかを**実際にコンパイルして確かめてから**答えたので、
  「たぶん書けない」で押し問答にならなかった（`AGENTS.md`「設計判断の確認」）
