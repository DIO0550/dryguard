## ゴールと結果

Issue のゴールは 1 つで、**達成した**。

| ゴール | 結果 |
|---|---|
| オーバーロードされた関数について、表示された 1 本ではなく**集合として**型シグネチャを比べられるようにする | 比較の単位を `TypeSignature`（1 本）から `OverloadSet`（呼べる型シグネチャの並び）へ移した。オーバーロード宣言の位置を指した hover を本数分送って集合を揃え、揃えられなければ `OverloadSetMiscounted` で測れないにする |

Issue が「決めること」として挙げた 3 点は、いずれも Issue のコメントに根拠つきで残した。

| 決めること | 決めたこと |
|---|---|
| 集合をどう取るか | 構文木で宣言の位置を決め、**今ある hover を本数分送る**（`signatureHelp` / `documentSymbol` は却下） |
| 集合として比べるとはどういうことか | **並びごと同じ**を要求（包含関係・順序を問わない 1 対 1 はどちらも却下） |
| 取れなかったときの倒し方 | サーバが数えた本数と構文木の宣言数を突き合わせ、食い違えば集合を組み立てない |

**ずれ: Issue 本文が書いた「今の倒れ方」が実際と違っていた。** Issue は
「表示された 1 本と件数が同じなら、隠れているオーバーロードが違っても単一化可能と答える」
としていたが、`normalized_outcome_of` に綴りを直接渡して確かめると `UnreadableSignature`
に倒れていた（`(+1 overload)` が戻り値の型の位置に残り、型として構文解析できないため）。
**倒れる向きは偽陽性ではなく偽陰性**だった。ゴールそのものは変わっていない。

ただし**穴が無かったわけではない**。集合の組み立てを飛ばして `(+N overload)` を剥がす
だけにすると、実サーバで Issue の言う偽陽性が再現する
（`test_two_functions_differing_only_in_a_hidden_overload_are_not_unifiable` が落ちる）。

**スコープを 1 つ広げた。** `type_references_of` が受けるノードを複数にし、
オーバーロード宣言に書かれた型名も集めるようにした。集合として比べ始めると、宣言にだけ
現れる型名が解決されず**開かれないエイリアスが比較に残る綴りへ現れる**ため、
広げないとこの PR 自身が新しい偽陽性を作る。分けなかった理由は Issue に書いた。

### A. 束縛された型変数に外側のエイリアスが差し込まれる（1 巡目 P1）

- 出どころ: レビュー（Codex P1、`src/syntax/type_reference.rs`）
- 内容: 「宣言をまたいで型名を 1 つに畳むと、`<T>(x: T): T` の束縛された `T` に
  外側の `type T = number` が差し込まれ、シグネチャが変わる」という指摘。

  差し込みの位置を決める `substitutable_type_name_spans_of` が `BoundNames::Excluded` で
  束縛名を外しているため起きない。`T -> number` を解決済みにして
  `normalized_outcome_of` に綴りを直接渡すと、束縛側は `%0`（型変数の付け替え）のまま、
  束縛の無い側だけが `number` に差し込まれた
- 既存ルール: 該当なし（欠陥として成立していないため）

### B. 同じ指摘が 2 巡目に再提起された（2 巡目 P2）

- 出どころ: レビュー（Codex P2、`src/semantics/type_signature.rs`）
- 内容: A と同趣旨で、`type T = number; function f<T>(x: T): T; function f(x: T): T;`
  という具体例つき。**同じスレッドの 2 巡目なので、綴りを直接渡す形ではなく
  実サーバ・本番の経路**（`traced_type_names_of` → `opened_type_names_of` →
  `type_signature_outcome_of` の集合の枝）で走らせて確かめた:

  ```
  f: [ { type_parameters: [_], parameters: ["%0"], return_type: "%0",
         declarations: [TypeDeclaration { name: "T", site: d.ts:1 }] },
       { type_parameters: [],  parameters: ["number"], return_type: "number",
         declarations: [] } ]

  g: [ { type_parameters: [_], parameters: ["%0"], return_type: "%0", declarations: [] },
       { type_parameters: [],  parameters: ["number"], return_type: "number",
         declarations: [] } ]
  ```

  1 本目は `%0`（型変数の付け替え）のままで `number` に置き換わっていない。
  **倒れる向きは指摘と逆**で、`f` の 1 本目だけが `declarations: [T @ d.ts:1]` を持つため
  `f` と `g` は `Unifiable` ではなく `NotUnifiable`（偽陰性）になる。

  この偽陰性は束縛名を**数える側**（`declared_type_names_of`）が返すことによるもので、
  `rules/coding.md`「同じ一覧を、安全な倒れ方が違う 2 箇所で使い回さない」が意図して
  選んだ向き（外すと pr-148 指摘 1 が直した偽陽性へ戻る）。**この PR が広げたのは
  「その状況に入りうる組み合わせ」で、倒れる向きは変えていない。**
- 既存ルール: 該当なし（欠陥として成立していないため）
