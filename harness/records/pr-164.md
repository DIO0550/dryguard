## ゴールと結果

Issue のゴールは 1 つで、**達成した**。

| ゴール | 結果 |
|---|---|
| オーバーロードされた関数について、表示された 1 本ではなく**集合として**型シグネチャを比べられるようにする | 比較の単位を `TypeSignature`（1 本）から `OverloadSet`（呼べる型シグネチャの並び）へ移した。オーバーロード宣言の位置を指した hover を本数分送って集合を揃え、揃えられなければ `OverloadSetMiscounted` で測れないにする |

Issue が「決めること」として挙げた 3 点は、いずれも Issue のコメントに根拠つきで残した。

| 決めること | 決めたこと |
|---|---|
| 集合をどう取るか | 構文木で宣言の位置を決め、**今ある hover を本数分送る**（`signatureHelp` / `documentSymbol` は却下） |
| 集合として比べるとはどういうことか | **並びごと同じ**を要求（包含関係・順序を問わない 1 対 1 はどちらも却下） |
| 取れなかったときの倒し方 | サーバが数えた本数と構文木の宣言数を突き合わせ、食い違えば集合を組み立てない |

**Issue 本文の「倒れる向きは偽陽性」は正しかった。** PR 本文と Issue コメントで
「実際は `UnreadableSignature` に倒れており、向きは偽陰性だった」と訂正したが、
**その訂正のほうが誤り**だった。`normalized_outcome_of` の戻り値（シグナルの層）だけを見て、
判定の層まで辿っていなかった。

`compare` を通して測ると、隠れているオーバーロードだけが違うペア（同じディレクトリ・
同じ依存先＝置き場所の判定が `Same`）はこうなる:

```
=== PR #164 の前（780b2a7） ===
[EXTRACT-CANDIDATE] /tmp/ovl2/src/a/parse.ts:5 <-> /tmp/ovl2/src/a/read.ts:5
  型シグネチャ: 測れない (返った綴りを読み解けない) → どちらでもない
  提案: 共通化してよい。1 つにまとめる先を検討する。

=== PR #164 の後（caa62b3） ===
[REVIEW] /tmp/ovl2/src/a/parse.ts:5 <-> /tmp/ovl2/src/a/read.ts:5
  型シグネチャ: 単一化不能 → 共通化しない側
  提案: 判断材料が足りない。人が見て決める。
```

`parse` は `string→string` / `number→number`、`read` は `string→string` / `Date→Date` で、
表示される 1 本は同じ綴り。**PR #164 の前は「共通化してよい」と答えていた** ——
Issue が書いたとおりの偽陽性で、利用者に見える層ではそれが出ていた。

経路は `src/classification.rs` にある。`UnreadableSignature` は `Lean::Neither` になり、
`shared_domain_verdict_of` が `stage1_shared_domain_verdict_of` へ落ちて、置き場所が
`Same` なら `ExtractCandidate` を返す（146-171 行）。正しい `NotUnifiable` なら
`Lean::TowardDoNotExtract` で `Review` になる。**シグナルの層で「測れない」でも、
判定の層では緩む側へ倒れる。**

**スコープを 1 つ広げた。** `type_references_of` が受けるノードを複数にし、
オーバーロード宣言に書かれた型名も集めるようにした。集合として比べ始めると、宣言にだけ
現れる型名が解決されず**開かれないエイリアスが比較に残る綴りへ現れる**ため、
広げないとこの PR 自身が新しい偽陽性を作る。分けなかった理由は Issue に書いた。

**ゴールは達成したが、機能の限界を 1 つ持ち込んだ**（指摘 4 / 5）。

### 1. 静的メンバーのオーバーロード宣言を、同じ名前のインスタンスメソッドに結び付けていた

- 分類: `plan`
- 出どころ: レビュー（Codex P1、1 巡目）
- 内容: 宣言を集める範囲を「同じスコープにある**同じ名前**の宣言」とした根拠は
  「TypeScript は同じスコープに同名の実装を 2 つ置けない」だったが、**クラスは同じ名前の
  静的メンバーとインスタンスメンバーを持てる**ので前提が足りていなかった。

  ```ts
  export class C {
    static scale(a: string): string;
    static scale(a: unknown): unknown { ... }
    scale(a: number): number { ... }        // 実体は (number) => number
  }
  ```

  インスタンスの `scale` に静的な側の宣言が結び付き、**`(string) => string` という
  別のメソッドの型**を返していた。

  **倒れる向きは 1 つに決まらない。** 誤った型を返すので、**どちらへ倒れるかは
  比べる相手で決まる**。修正前のコード（`77437eb`）で両方を測った:

  | 比べる相手 | 出た型シグネチャ | 正しい答え | 判定 | 向き |
  |---|---|---|---|---|
  | `strPeer(a: string): string` | 単一化可能 | 単一化不能 | `EXTRACT-CANDIDATE` | **偽陽性** |
  | `numPeer(a: number): number` | 単一化不能 | 単一化可能 | `REVIEW` | **偽陰性** |

  修正後（`caa62b3`）は同じ 2 つが順に `単一化不能` / `単一化可能` になり、どちらも
  正しい側へ出る。

  **この PR が用意した安全網（本数の突き合わせ）がすり抜ける形だった。** 静的な宣言 1 本 :
  インスタンスの hover 1 本で本数が 1 対 1 に揃うため、`OverloadSetMiscounted` は発火しない。

  `8285226` で絞り込みに静的 / インスタンスの側を足し、`75f0636` で回帰テストを 2 件
  （対照込み）足した。
- 既存ルール: `AGENTS.md`「実装を始める前に」（`分類: plan` = 計画の誤り・不足）。
  **宣言を集める範囲を決めるとき、同じ名前が指しうる別のメンバーを計画に入れていなかった。**

  `rules/coding.md`「列挙で判定を組むときは、漏れの倒れる向きを選ぶ」も候補だが採らない。
  一覧（`OVERLOAD_DECLARATION_KINDS`）の漏れではなく**絞り込みの軸そのものの欠落**で、
  倒れる向きの選び方の話ではないため。`分類:` は 1 つしか持てず `count.sh` はその行しか
  数えないので、起点にあたる `plan` を採る（`AGENTS.md`「既存の `plan` に当たる指摘は、
  引き続き `plan` に分類する」）。
- 次にどう防ぐか: 今回は記録のみ。**新しい観点の候補として残す** —

### 3. サーバが数えた本数が 0 を表現できる型のままだった

- 分類: `smart-constructor`
- 出どころ: レビュー（Codex P2、2 巡目）
- 内容: `counted` は「綴られている 1 本 + 要約が数えた本数」なので 0 にならないのに、

  `NonZeroUsize` にし、元になる `CountedSignature::overloads` まで替えた

  できる」と書いた検出にあたる。

  `counted.overloads.get() == overload_positions.len()` かつ `counted` は 1 以上なので、
  位置は必ず 1 つ以上あり、失敗する回は早期に返るため
- 既存ルール: `rules/coding.md`「生成時に検証し、不正な値を存在させない」

### 4. 束縛された型変数に、外側の同名エイリアスの宣言が結び付く（1 巡目）

- 分類: `missing-signal`
- 出どころ: レビュー（Codex P1、1 巡目・`src/syntax/type_reference.rs`）
- 内容: 指摘は「宣言をまたいで型名を 1 つに畳むと、`<T>(x: T): T` の束縛された `T` に
  外側の `type T = number` が**差し込まれる**」だった。**差し込みは起きない** ——
  位置を決める `substitutable_type_name_spans_of` が `BoundNames::Excluded` で
  束縛名を外している。

  **ただし同じ箇所に別の欠陥があった。** 差し替える側と違い、**数える側**
  （`declared_type_names_of`）は束縛名も返すので、束縛された `T` に外側の `T` の
  **宣言の場所**が結び付く。構造が同じ 2 つの集合が、それだけで別物になる。

  実測（`/tmp/ovl4`、`f` は同じファイルに `type T = number` を持ち `<T>` を束縛する。
  `g` は `T` を持たない。両者の集合は構造として同じ）:

  ```
  f: [ { type_parameters: [_], parameters: ["%0"], return_type: "%0",
         declarations: [TypeDeclaration { name: "T", site: f.ts:3 }] },
       { type_parameters: [], parameters: ["number"], return_type: "number",
         declarations: [] } ]

  g: [ { type_parameters: [_], parameters: ["%0"], return_type: "%0", declarations: [] },
       { type_parameters: [], parameters: ["number"], return_type: "number",
         declarations: [] } ]
  ```

  違いは**束縛された名前に付いた `declarations` だけ**で、比較に残る綴りは
  どちらも `%0`（付け替え後）と `number`。`compare` を通すと:

  ```
  === PR #164 の前（780b2a7） ===
  [EXTRACT-CANDIDATE] f.ts:7 <-> g.ts:5
    型シグネチャ: 測れない (返った綴りを読み解けない) → どちらでもない

  === PR #164 の後（caa62b3） ===
  [REVIEW] f.ts:7 <-> g.ts:5
    型シグネチャ: 単一化不能 → 共通化しない側
  ```

  **正しい答えは「単一化可能」**（集合は構造として同じ）で、そのときの判定は
  `EXTRACT-CANDIDATE`。PR #164 の後は**確かめた答えとして「単一化不能」を出しており、
  偽陰性**になる。前は「測れない」だったので、**答えが「測れない」から
  「確定した誤り」へ変わった**のがこの PR の持ち込んだ限界。

  この形が届くようになったのは 2 つとも PR #164 の変更による。オーバーロードされた関数は
  以前は綴りが読めず `UnreadableSignature` で止まり、`traced` も実装のノードの型名しか
  持っていなかった
- 既存ルール: `rules/architecture.md`「取れなかったシグナルを既定値で埋めない」の
  「どこまでを「取れなかった」に数えるか」。同節の
  「**比較には残らない綴りを根拠に別物と答える**ことになる」がこの形にあたる
  （付け替えで `%0` になった名前は比較に残らないのに、その宣言が答えを決めている）。

  束縛名を数える側から外すと `rules/coding.md`「同じ一覧を、安全な倒れ方が違う
  2 箇所で使い回さない」が直した偽陽性（pr-148 指摘 1）へ戻るので、**単純な反転では直らない**
- 次にどう防ぐか: 今回は記録のみ。**直す先が pr-148 の判断と衝突する**ので、
  Issue を分けて設計から決める話になる（`AGENTS.md`「設計判断の確認」）
