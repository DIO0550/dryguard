## ゴールと結果

Issue のゴールは「Phase 0 の素朴な切り出しを tree-sitter に置き換え、**関数・メソッド・
impl ブロック単位**で確実にチャンク化できるようにする」。完了条件は
「Phase 0 で切り出せていたものが漏れなく取れ、かつ Phase 0 では取りこぼしていた形も取れる」。

**満たした。** 既存の切り出しテスト 17 件・import 収集テスト 8 件・統合テスト 12 件は、
バリアント名の変更 1 件（`UnterminatedFunction` → `UnparsableFunction`）を除きそのまま通る。
取りこぼしていた形として、次の 5 つを新たに切り出せるようにした。

| 形 | Phase 0 で取れなかった理由 |
|---|---|
| 複数行シグネチャ | `): number {` だけの行を `is_function_header` が関数の始まりと読めない |
| 本体ブロックを持たないアロー関数 | `(v) => v * 2;` はブレースで終わらない |
| オブジェクトのメソッド | 行の見た目では拾えるが、範囲がオブジェクト側とずれる |
| 関数式 / ジェネレータ関数式 | 同上 |
| ジェネレータ関数宣言 | 同上 |

実ファイルでも確かめた。`tests/fixtures/` の既存 3 組の構造類似度は **0.94 / 0.88 / 0.59 のまま
変わっていない**（切り出せる範囲は広がったが、既存の判定は動いていない）。複数行シグネチャの
2 ファイルを新たに作って `compare` に通し、Phase 0 では `NoEnclosingFunction` になっていた
位置から判定が出るところまで確認した。

**スコープの読み替えを 1 つした**: Issue の「impl ブロック単位」は Rust の構文で、
TypeScript の grammar には無い。`CHUNK_KINDS` には入れず、Phase 4（Rust 対応）で
grammar ごと足すものとして doc に書いた。この読み替えは PR 本文と Issue に書いてある。

**ずれ**: 1 つ。`Chunk::source()` の採り方を実装中に変えた（→「手戻り」1）。

## 手戻り

3 回。**いずれもコミット前に自分で気付いて直したもの**で、指摘としては数えていない
（pr-76 の「`Reason::lean()` を書いてから消した」と同じ扱い）。

1. **`Chunk::source()` の採り方を、計画から変えた。** Issue に投稿した計画では
   「チャンクノードそのもののテキスト」とし、`export ` が落ちること・既存の assert 2 件を
   直すことまで織り込んでいた。実装中に 2 つ理由が出て、行ごと採る形に変えた。

   - `SyntaxTree::text_of` はバイト範囲が文字境界に乗らないと `None` を返す。本番コードで
     `unwrap` は使えないので、`ChunkingError` に**テストで落とせないバリアント**を足すことになる
   - `Chunk` は `lines` と `source` を両方持ち、`Chunk::new` の doc が「食い違ったチャンクを
     作れないようにする」と言っている。ノードのテキストは行の途中から始まりうるので、
     **この不変条件が構造ではなく注意で保たれる形**になる

   結果として Phase 0 の出力がそのまま残り、直す予定だった assert 2 件も不要になった。
   **計画に書いた根拠（`export ` は構造ではないので落ちるほうが正しい）自体は今も妥当**だが、
   それより不変条件のほうが重い、という順序を計画時に見落としていた。

2. **落ちようのないテストを 1 件書いて、差し替えた。** 内側のノードをバイト範囲で選ぶ根拠として
   `() => () => 1` を挙げ、テストも書いた。しかし `Chunk` が外に見せるのは行範囲と行ごとの
   ソースだけなので、**1 行に収まった入れ子は外側を選んでも内側を選んでも同じ `Chunk` になる**。
   `rules/testing.md`「assert は『落ちうるか』で見る」に反するので消し、行をまたぐ入れ子
   （関数の中のアロー）のテストに置き換えた。`innermost_chunk_node` の doc からも、
   支えられない Why not を落とした。

3. **`generator_function` を守るテストが無いことに、ミューテーションで気付いて足した。**
   `CHUNK_KINDS` に 6 種別を並べたが、テストで守られていたのは 5 種別だけだった（→「うまくいったこと」2）。

## うまくいったこと

1. **ノード種別を推測せず、別プロジェクトで grammar を叩いて確かめてから計画を書いた。**
   `function_expression` / `generator_function`（式）と `generator_function_declaration`（宣言）が
   別種別であること、クラスとオブジェクトのメソッドが同じ `method_definition` であること、
   `import_statement` と `export_statement` がどちらも `source` フィールドを持つことは、
   ドキュメントを読むだけでは取り違えやすい。`AGENTS.md`「実装を始める前に」の
   「計画の入力を鵜呑みにしない」を、Issue の記述だけでなく**外部ライブラリの挙動**にも当てた形。

2. **疑わしい assert に変異を入れて確かめた**（`rules/testing.md`「迷ったら、その 1 件だけ
   実装を壊して走らせる」）。6 件試して、うち 1 件はテストの穴を見つけた。

   | 入れた変異 | 落ちたテスト |
   |---|---|
   | `enclosing.has_error()` → `false` | `..._that_never_closes_returns_unparsable_function` |
   | ノードの部分木 → 木全体のエラーを見る | `..._next_to_a_broken_one_is_still_taken` |
   | `min_by_key` → `max_by_key` | 入れ子の内側を選ぶテスト 2 件 |
   | `CHUNK_KINDS` を 1 種別に削る | 9 件（**`generator_function` だけ落ちず、穴が見つかった**） |
   | `is_dynamic_import` を「呼び出しなら何でも」に | `..._ignores_a_require_call` |
   | `source` フィールド → 部分木の最初の文字列 | `..._ignores_an_export_that_has_no_source` |

3. **移行で黙って減る依存先に気付いて拾った。** Phase 0 の「直前の語が `import` / `from` なら
   次の文字列を拾う」規則は `import("./x")`（動的 import）も拾っていた。`import_statement` だけを
   見る形にそのまま移すと、遅延読み込みしているファイルの依存先が消えて重なりの値が動く。
   grep では見えない差だったので、**Phase 0 の実装を読み直して挙動を数え直した**。

4. **誤ったレビュー指摘に、証拠を出して反論しつつ、指摘が指している欠落は直した。**
   言われたとおりに直すと壊れる指摘だったが、「読み違いが起きた」という事実のほうを拾って
   Why を足した。指摘を丸ごと退けても、丸ごと受け入れても、どちらでも悪くなる形だった。

5. **スコープを広げなかった。** AST 正規化（#20）・類似度の置き換え（#21）・`scan`（#22）は
   同じ Phase 1 の中にあり、トークン化だけが文字走査のまま残る中途半端な状態になるが、
   **同じ回にトークンの語彙と類似度が両方動くと落ちたときの原因の範囲が広がる**ので入れなかった。
   代わりに `token.rs` の doc に「ここだけ Phase 0 のまま」と、それがどの回で変わるかを書いた。
