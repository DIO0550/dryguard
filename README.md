# dryguard

**構造の似たコードが偶発的な重複かどうかを、理由付きで判定する CLI。**

AI コーディングエージェントは、テキスト的に似たコードを見つけると安易に共通化する。
しかし「テキストが似ている」と「変更理由が同じ」は別物で、偶発的な重複
(incidental duplication) を共通化すると間違った抽象化が生まれる。

このツールは、似たコードペアを検出するだけでなく、**型・依存・参照の意味情報から
「共通化してよいか / すべきでないか」を理由付きで分類する**。

| ラベル | 意味 |
|---|---|
| `EXTRACT-CANDIDATE` | 構造・型・依存ドメインが一致し、同じ位置で差し替わる名前・リテラルも無い。共通化してよい |
| `DO-NOT-EXTRACT` | 構造は似ているが依存先・呼び出し元のドメインが別。偶発的重複 |
| `REVIEW` | 中間ケース。人間の判断が要る |

## 差別化ポイント

1. **「共通化するな」を言える。** 検出だけのツールは重複を報告するだけで、共通化の是非は判断しない
2. **判断に理由が付く。** ML・埋め込みを使わずルールベースにするのは、説明可能性がこのツールの価値そのものだから
3. **AI エージェント向けの出力。** 人間のリファクタリング支援ではなく、エージェントの自己修正ループに組み込む JSON が一級市民

## 状態

**Phase 2（途中）。** 引数の受け口・関数チャンクの切り出し・構造類似度・
依存モジュールの重なり・モジュール距離に加えて、**型シグネチャが単一化できるかと
呼び出し元がどのドメインから来ているか**（Stage 2）を判定へ渡している。
5 つのシグナルを統合して 3 ラベルと、シグナルごとの理由・提案を出す。
判定に当てる閾値は `--threshold` > `dryguard.toml` > 既定値の順に決まる。

意味情報は **LSP サーバを子プロセスで起動し、自前の JSON-RPC で握手して
hover / references を尋ねる**。**サーバを使えない環境でも判定は動き**、
そのときは Stage 1 のシグナルだけで判定して「測れない (LSP サーバを使えない)」を
出力に出す。今つないでいるのは `compare` だけで、`scan` の候補ペアへの配線はまだ。

Stage 1 のうち**チャンクの切り出しと import の収集は tree-sitter** に載っている。
`scan` はコードベース全体を総当たりで比べ、**ファイルの解析とペアの比較は rayon で
並列に回す**（出力の並びは逐次で回したときと変わらない）。

トークン列の長さから出る**上限で、閾値に届かないペアの突き合わせを省く**。
省いた数は走査した量に出る。上限は実際の類似度を下回らないので、
**候補ペアは省かないときと 1 組も変わらない**。候補を落とす種類の事前フィルタ
（MinHash/LSH・ブルームフィルタ）はまだ無く、比較の数も n² のまま。

進め方は**縦切り（walking skeleton）**で、各ステージを順に完成させるのではなく
全ステージを雑に貫通させてから厚くする。計画は [`docs/dryguard-plan.md`](docs/dryguard-plan.md)、
分割した作業は [Issues](https://github.com/DIO0550/dryguard/issues)。

## アーキテクチャ

```
[Stage 1: 候補抽出]      [Stage 2: 意味情報収集]   [Stage 3: 分類]
 syntax                   semantics                classification
 tree-sitter              LSP                      ルールエンジン
  ├ 関数/メソッド単位で    ├ hover (型シグネチャ)     ├ シグナル統合
  │ チャンク化            ├ callHierarchy           ├ ドメイン距離判定
  ├ AST正規化             ├ references              └ 理由付きラベル
  └ 類似ペア列挙          └ documentSymbol
```

## 使い方

```bash
cargo run -- compare <locA> <locB>   # 特定の 2 関数を比較 (file:line)
cargo run -- scan [path]             # コードベース全体をスキャン (既定は .)
cargo run -- check --diff [rev]      # git の差分に含まれる関数を起点に、全体と比較 (既定は HEAD)
cargo run -- check --diff --staged   # ステージ済みの変更だけを起点に、index の版の全体と比較

オプション:
  --lang ts|rust|auto
  --format text|json
  --threshold <0-1>
  --explain                          # 判定根拠のシグナル値を全表示
  --fail-on do-not-extract           # 非推奨ペアがあれば exit 1 (LSP に尋ね切れなければ exit 2)
  --include-tests                    # scan / check のみ。Rust / TypeScript のテスト関数も比較する (既定は外す)
```

`scan` は Rust のテスト属性（`#[test]` / `#[tokio::test]` など）付き関数と、
TypeScript / TSX の `describe` / `it` / `test`（`.only` / `.skip` も対応）の第2引数に
直接書いたアロー関数・関数式を除外する。コールバック側の括弧・型アサーション等は辿る。
ファイル名では除外せず、ヘルパーやテスト本体内の通常の関数は残す。除外数は走査結果に出る。
`--include-tests` で再び比較対象にでき、`compare` での直接指定には影響しない。

TypeScript 側は呼び出し名によるヒューリスティックなので、同名の業務 API も対象になる。
import 別名・namespace・`each`・`beforeEach` 等のフック・修飾の連鎖・callee 側の括弧は認識しない。
spread 引数の後ろも引数位置が確定しないため残す。テスト全体を取り除く機能ではない。

終了コードは 3 つ。**判定で落ちたのか、判定を答えとして読めないのかを CI が区別できる**ように分けてある。

| コード | 意味 |
|---|---|
| 0 | 判定を出し終えた（`--fail-on` を付けたなら、その判定は出ず、候補ペアを LSP に尋ね切れた） |
| 1 | `--fail-on` に指定した判定が 1 件以上出た（`compare` はそのペア、`scan` / `check` は候補ペアのいずれか）。判定の出力は stdout にそのまま出る。LSP に尋ね切れなかったときは 2 になる |
| 2 | 判定を出せなかった（引数・設定の誤り、チャンクを切り出せない、走査を始められない、git の差分を取れないなど）か、`--fail-on` を付けて**候補ペアを LSP に尋ね切れなかった**（判定の出力は stdout に出る） |

**`--fail-on` を付けたときは、LSP に尋ね切れなかった回を成功にしない。** サーバが見つからない・
握手に失敗した・問い合わせの往復が落ちたなどで候補ペアの Stage 2 を尋ね切れなかったら、
判定を stdout に出し終えたうえで終了コード 2 にし、理由を stderr に出す。成功（0）にすると、
検査されなかったのか通ったのかを CI が区別できない。`--fail-on` に指定した判定が出ていても
1 ではなく 2 にする（1 は「判定を出し終えた」ときの答えで、1 を見た CI は環境の故障を
見落とす）。そのときも、出た件数の行は stderr に残す。
取れなかったシグナルは、判定の根拠（text の根拠の行・JSON の `status`）にも理由付きで出る。

- 候補ペアでないので尋ねなかったペア・サーバは答えたがシグナルが「測れない」だったペアは数えない
  （前者は Stage 2 で判定が変わらない。後者は理由が根拠の行に出る）
- dryguard が LSP サーバを持たない言語の候補ペアも数えない（今は TypeScript / Rust のどちらにもサーバがある）
- `--fail-on` が無ければ、LSP サーバが使えなくても判定を出して 0 で終わる
  （取れなかったシグナルは根拠に出る）

`--fail-on` が取る値は `do-not-extract` だけ。`REVIEW` は取れなかったシグナルが寄る側でもあり、
それで落とすと判定の質に関わらず止まるフックになる。

`--explain` を付けると、根拠の行に 2 つが加わる。**LSP へ尋ねなかったシグナル**（理由付き）と、
**各シグナルに当てた閾値**。**既定でも判定に効いた根拠は出る**ので、`--explain` は
結論に理由を足すのではなく、**閾値との突き合わせまで見せる**ためのもの。

`scan` は `.ts` / `.tsx` / `.mts` / `.cts` / `.rs` を見る。`--lang ts` / `--lang rust` で
対象を絞り、`auto` では両方を走査する（異なる言語の関数同士は比較しない）。Rust の
自由関数・`impl` 内のメソッド・トレイト実装のメソッドをそれぞれ 1 チャンクにする。
正規化トークンが下限（`syntax::token` の `MINIMUM_TOKEN_COUNT`）に届かない関数（1〜3 行のアクセサ・委譲）は `scan` では比べず、
外した数を走査量の行に出す（`compare` は名指しされれば比べる）。
`.java` はメソッド・コンストラクタをチャンクにでき、`compare` は名指しされれば比べるが、`scan` の走査にはまだ入らない（import・葉の綴りの違い・型シグネチャは Java の読み方がまだ無い）。
`.swift` は関数・メソッド・`init` / `deinit` をチャンクにし、`compare` で名指しすれば比べるが、
正規化トークン・依存の宣言の対応がまだ無いので、`scan` は走査しない。
CLI は拡張子から TypeScript と Rust の LSP サーバを選ぶ。`scan --lang auto` では
言語ごとに候補を揃え、TypeScript は typescript-language-server、Rust は rust-analyzer の
セッションで hover / references を問い合わせる。Rust の型シグネチャ比較は #40 まで
「測れない」。

`node_modules` / `dist` / `build` / `target` / `.git` は
降りない。**読むときの grammar は拡張子で選ぶ**（JSX は TypeScript の grammar では読めず、
型アサーション `<T>value` は TSX の grammar では JSX に見えるので、片方で兼ねられない）。
読めなかったファイルと構文エラーで切り出せなかった関数は、
**候補ペアの後ろに一覧で出す**（黙って飛ばすと、対象だったのか除外されたのかが分からない）。

`--format json` は**エージェントに読ませて自己修正させる用途**の出力
（`docs/dryguard-plan.md`「差別化ポイント」）。**text に出る情報は JSON にも出る** ——
ラベル・両側の位置・シグナルごとの値と傾き・提案が入り、測れなかったシグナルは
`status` と `reason` のキーで理由まで出る。**`--explain` は JSON にも同じように効く**
（尋ねなかったシグナルと、当てた閾値が増える）。
**スキーマはまだ固定していない**ので、シグナルの構造が変わると形も変わる（Phase 5 で安定化）。

`check --diff` は、**変更した関数が既存のコードと偶発的に重複していないか**を見る
（エージェントの自己修正ループ・pre-commit フック向け）。カレントディレクトリの作業ツリーを
指定したリビジョン（既定は `HEAD`）と比べ、変わった行を含む関数を起点に、
**変わっていない関数も含めたカレントディレクトリ以下の全体**と比べる。両側とも変わっていない組は比べない。

- 比べるのは作業ツリーとリビジョンなので、ステージ済みと未ステージの変更の両方が入る。
  まだ追跡していないファイル（`.gitignore` で外したものを除く）は全行が変わったものとして扱う
- 範囲（`main..HEAD`）は受け付けない。行番号がチャンクを切り出す版を指さなくなるため
- 消しただけの変更は、消した点を内側に含む関数だけを「変わった」とする
- 走査量の行（JSON は `walked.changed_chunks`）に変わった関数の数を出す。
  **変更が無かったのか、変えたが似たコードが無かったのか**はこの数で読み分ける
- git が無い・作業ツリーの外・リビジョンを解決できないときは終了コード 2。
  **コミットが 1 つも無いリポジトリでは `HEAD` を解決できない**ので、最初のコミットの後から使う

`check --diff --staged` は、作業ツリーではなく**ステージ済みの変更（index）**をリビジョンと比べる
（`git diff --cached` と同じ範囲。pre-commit フック向け）。`--diff HEAD~1 --staged` のように
リビジョンと組み合わせられる。

- **関数の切り出しも、比べる相手も、index の版から読む。** 部分的にステージした
  （`git add -p`）ファイルでも、位置は index の版の行番号を指す
- コミットに入らないものは比べない。未追跡のファイルは起点にも相手にもならず、
  作業ツリーから消しただけ（ステージしていない）のファイルは相手に入る
- index に未解決のマージ衝突があると終了コード 2（どの版を読むかが決まらない）

**既知の制約**: index の版で揃うのは関数の切り出しと、LSP サーバに開かせる候補ペアのファイルまで
（揃えるのは Issue #365）。次のものは**作業ツリーの版**を読む。

- 型名の宣言側・参照元として読むファイル（Rust のエイリアス・関連型・配列長の評価、
  参照元のテスト範囲の判別）と、LSP サーバが自分で読むファイル。**候補ペアのファイル自身も、
  宣言側・参照元として読むときは作業ツリーの版を読む**（同じファイルの `#[cfg(test)] mod tests` など）。
  **ステージしていない変更が残ったファイル**をここで読むと、index の版で数えた位置を
  別の版に当てることになり、測れない側に倒れるだけでなく**別の宣言・範囲を読んだ答えが出ることがある**
- `dryguard.toml`（ステージしただけの設定の変更は効かない）
- 作業ツリーの走査が含めていた、追跡していないファイル（`.gitignore` で外したものを含む）と
  サブモジュールの中のファイルは、index に無いので相手に入らない。`git add -N` で足しただけの
  ファイル（コミットには入らない）は、中身が空のものとして読むので関数が出ない

## 閾値の設定

閾値は 3 つあり、**カレントディレクトリの `dryguard.toml`** で動かせる。

```toml
[thresholds]
structural_similarity = 0.5   # 構造が似ていると見なす下限。`--threshold` と同じもの
shared_imports = 0.5          # 依存先を共有していると見なす重なりの下限
shared_caller_domains = 0.5   # 呼び出し元を共有していると見なす重なりの下限
```

**優先順位は `--threshold` > `dryguard.toml` > 既定値。** 書かなかったキーは既定値のまま。
ファイルが無ければ全部が既定値で、**設定を置かずに使える**。

**書式が違えば走らない。** 知らないテーブル・知らないキーの綴り・同じキーの 2 度目・
0.0-1.0 の外の値は、**どのファイルの何行目がなぜ駄目か**を出して終了コード 2 で止まる。
黙って既定値に落とすと、設定したのに効いていないことを出力から確かめられない。

ディレクトリの段数（別ドメインと見なす隔たり）は**外に出していない** ——
0.0-1.0 の閾値ではなく、調整したくなった記録もまだ無い。

## ドメインの宣言

ドメインは既定では**ファイルのすぐ上のディレクトリ**から推定する。推定が外れる置き方
（`controllers/` `services/` のように層で分けて、1 つのディレクトリに複数の機能が並ぶ形など）
では、同じ `dryguard.toml` の `[domains]` にパスの glob を並べて宣言できる。

```toml
[domains]
billing = ["src/billing/**", "src/**/invoice*.ts"]
inventory = ["src/inventory/**", "src/**/product*.ts"]
```

- glob は **`dryguard.toml` を置いたディレクトリからの相対**。書けるのは `**`（0 段以上）と
  `*`（1 つの段の中の任意の綴り）だけで、それ以外（`?` `[` `{` など）は書式の誤りとして止まる
- **宣言が推定に勝つ。** 宣言に当たったファイルは、モジュール距離・呼び出し元ドメイン・
  呼び出し先ドメインのどれでも、ディレクトリの代わりに宣言の名前で数える。
  どの宣言にも当たらないファイルは今までどおりディレクトリで数え、**宣言の名前とは一致しない**
- **1 つのファイルが名前の違う 2 つの宣言に当たると、黙ってどちらかを選ばない。**
  比べるファイルなら判定の前に終了コード 2 で止まり、参照元・呼び出し先のファイルなら
  そのシグナルが「測れない」になって、どのファイルがどの 2 つに当たったかが出る
- 宣言は**ファイル単位**まで。1 つのファイルに別の機能が同居する形は、呼び出し元の観測で分かれる
  （[#36](https://github.com/DIO0550/dryguard/issues/36)）

## 開発

```bash
cargo fmt --check                           # フォーマット検査（CI と同じ）
cargo clippy --all-targets -- -D warnings   # Lint（テストコードも対象）
cargo test                                  # テスト
bash harness/githooks/pre-push              # push 前の検査をまとめて
```

実装規約は [`AGENTS.md`](AGENTS.md) と [`rules/`](rules/)。
規約を強制する仕組みは [`harness/`](harness/) と `.github/workflows/`。
