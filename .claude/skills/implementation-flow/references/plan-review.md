# 計画の検証の観点

計画を検証するサブエージェントに、**Issue の本文・計画・この観点**をそのまま渡す。
サブエージェントはコードを書かず、指摘だけを返す。

**観点はこのリポジトリの記録から来たものだけを置く。** 移植元の観点を並べないのは、
`AGENTS.md`「実装を始める前に」の Why not（他リポジトリの項目をコピーしない）と同じ理由。
数えたのは `bash harness/records/count.sh` の `plan` の分類で、Rust 共通の観点は
プラグインの `coding-standards` / `tdd` / `testing` が持つ。

## 入力の網羅

- Issue が挙げた対象の一覧を、**grep で数え直したか**（`AGENTS.md`「実装を始める前に」の 1 項目目）
- Issue を立てた後のマージで、Issue の前提が古くなっていないか
  （`harness/records/pr-242.md` 指摘 1）
- 完了条件が、**機械的に確かめられる形**（grep・テストの名前・コマンドの出力）になっているか

## 置き場所

- `docs/dryguard-plan.md` の該当節が指す置き場所と合っているか
  （`AGENTS.md`「実装を始める前に」の 2 項目目）
- `rules/architecture.md`「3 ステージのパイプライン」の責務の表・「依存方向のルール（必須要件）」・
  「判定は 1 箇所にだけ置く」に反していないか
- ステージをまたぐ移動・再配置を含むなら、実装の前に止まって確認する計画になっているか
  （`AGENTS.md`「設計判断の確認」）

## 影響範囲

- 変える型・関数の**参照元・既存テスト・既存コメント**を、ファイル単位で割ってあるか
- `rules/*.md` が指している関数名・語を変えるなら、`rules/` の出し直しが計画に入っているか
  （`AGENTS.md`「実装を変えたら、rules/ 配下の記述も同じ PR で出し直す」）

## 前提の裏取り

- LSP サーバの応答・件数・実コーパスで測った数など、**走らせずに置いた前提**が無いか
- 測る母集団が、比べる相手と揃っているか

## テストの計画

- 先に書くテストが、**変えたい振る舞い**を表しているか（`rules/tdd.md`
  「判定ルールを変えるときは、先にテストを足す」）
- 既定値と違う答えになる入力・「出ない」を確かめるときの対照が選べているか
  （`rules/testing.md`「assert は「落ちうるか」で見る」）
- LSP を要するテストが、飛ばしたことが分かる形になっているか
  （`rules/testing.md`「LSP を要するテストは、飛ばしたことが分かる形にする」）

## 分割

- 分ける / 分けないの理由が、「独立してマージできるか」で書かれているか
  （`AGENTS.md`「タスクの分割」）
